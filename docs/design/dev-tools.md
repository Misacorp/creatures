# Dev tools: a debug panel for every view (staging only)

Status: **shipped 2026-10-13**: the server side (the gate, the dev clock and every tool in the table below, as `/api/dev/*` routes; see "Dev tools: the gate, the dev clock and where forced state lives" in `decisions.md`) and the client panel (`apps/activity/src/dev/`, see "Dev tools: the client panel" in `decisions.md`). Limits: the clock only moves forward (plus a reset to zero, and the raid bench's Clear the board, which moves it back to the real time at most), and the Analytics "roll up now" tool answers 501 until the rollup hook is wired. Plan written 2026-10-13. Misa: "improve dev tooling in the dev app: running simulated raids, sped up expeditions, setting dungeon rank, raid boss difficulty tier, etc. Basically a debug panel into every view that lets me set the game into a desired state for testing. This needs to be strictly in the dev environment."

## Safety (non-negotiable)

- **Server gate:**
  - A new Worker var, `DEV_TOOLS`, is `"on"` only in the staging environment in `wrangler.jsonc`, and `"off"` at the top level and in production. This is the same pattern as `RAID_PRACTICE`.
  - Every dev route is under `/api/dev/*` and returns a plain 404 unless `DEV_TOOLS === "on"`. (Unknown `/api/*` routes answer 401, because the session check comes first, so this 404 is not hidden.)
  - A test checks that the production config has it off, and that every dev route refuses when it is off.
  - These changes need PR callouts for `wrangler.jsonc`.
- **Server managers only (2026-11-06, Misa: "I don't want testers to have access to dev tools. Just me"):** on top of the var, every `/api/dev/*` route answers the same plain 404 to anyone who cannot manage the Discord server (not the owner, no Administrator, no Manage Server): `mayUseDevTools` in `dev-tools.ts`, which reuses `GuildCore.canManageServer` (the raid channel's check, with its 60 s per-player cache and in-flight sharing), so a player costs at most three Discord reads a minute, on staging only. It fails closed: when Discord cannot answer, or no bot token is configured, the answer is no. `/api/me` says `devTools: true` only for a manager; the public `/api/config` no longer says it at all (it cannot know who asks), so a tester's client never loads the panel chunk. The check runs after the route's tool name is known and before the body is read. No user id is written into config or the repo: the Discord server decides who Misa and any other admin is.
- **Client gate:**
  - The panel's code is in a separate lazily loaded chunk, imported only when the server's session or config response says dev tools are on.
  - The production build also strips it, through a Vite define.
  - Production users never download it.
- **Scope:** dev routes act only on the caller's own guild. Most act only on the caller's own player data. These act on the **whole staging guild**, so they affect every player in it: the clock, the raid test bench (raid-clear, raid-fill, raid-rank, raid-play), dungeon-modifiers, dungeon-seed and the Valley Games tools (games-bots, games-run-now, games-reset). `GET /api/dev/events` shows the guild's recent events (kind, time and props), without actors. Identity comes from the session, as always.
- **Not idempotent:** dev POSTs carry no idempotency key, so a retry grants twice. Accepted for a staging test tool.
- **The ledger stays append-only:** set-balances and `dungeon-reset` append `dev` entries (a negative one for what a reset takes back, never below a zero balance) and never delete ledger rows. Because the credits keep their idempotency keys, a run of the same day and attempt after a reset is not paid Bait or Essence again (gear grants of the day are deleted, so those can be granted again). Rollups ignore `source = 'dev'` ledger rows.
- **The dungeon on a map (2026-10-18, `dungeon-paths.md`):** the day is one map, redrawn from the day's seed. _Re-roll the day's seed_ clears the stored map (`map_json`), so the next look draws a new map; a run that is open keeps the map it started with. _Pick the day's modifiers_ is laid over the map when it is read (never stored): the first two entrance rooms (left to right, a third takes the first again) and the room boss take the picked three, which are also the three entries old clients read; the other rooms keep what the seed drew. _Reset today's run_ also deletes a run that is still open and its steps (nothing was paid for it, and it never touched the progress; a treat it was paid with stays spent). _Force the first-day retry_ turns a run that went home or cleared into a defeat, since only a defeat opens the retry. The separate `dungeon-map` tool of the design is not built: re-rolling the seed does the same.
- **The Valley Games (2026-10-22, `valley-games.md`):** _games-bots_ `{ count? }` (1 to 12, default 6) makes sure the raid's guests `dev-guest-1` to `-<count>` exist with at least six creatures each and enters them in every event of the next show day they left empty (they stay in the raid roster as they were; there is no auto-entry since 2026-10-23, so run it again for a later day); bots appear in the show and get no medals, badges, records or experience. _games-run-now_ `{ showInSeconds? }` (5 to 120, default 15) enters the guild's bots in the events of the next show day they left empty, then locks that day now, as the scheduler would (snapshots, the live seed), and starts its show then; the award follows at its end, and the next day keeps its own 13:37 lock. _games-reset_ `{}` forgets the latest locked day (its results and placings; its entries stay) so it can be played again; what it paid stays. A day reset after its own lock time locks again at once (a late lock shows 15 s later, or at 13:40 if that is later).
- **Combat v2 (2026-11-02, `combat/integration.md`):** _combat-v2-convert_ `{}` exists only when the `COMBAT_V2` flag is on as well (staging); it acts on the **whole staging guild**. Every creature that has learned no v2 talent rolls one from its line's pool as a fresh catch would (recorded in its player's line book, learned and slotted in slot 1), its saved Knack is cleared, and its player's finale ability choice for the open week goes. A creature that already has a v2 talent is left alone, so a second run changes nothing and never touches a Knack saved since. **It also rebuilds the raid week the clock is in as a combat v2 week when that is a v1 week** (a week takes its rules once, when it is created, so a staging clock that moved before the flag was on leaves v1 weeks): everything stored for that one week (the week row and every table keyed by it: parties, members, placements, results, events, swap requests, abilities, Auto fire, live finale rows, reveal marks, readiness, Festival grants) is deleted in one transaction and the week is created again by the normal path (the track's slot and boss). A v2 week is left alone, other weeks, the track, the ladder history and players' creatures and balances are not touched, and a second run changes nothing. The answer says `weekRebuilt`, `weekId` and `slot`. In the panel: Raid, _Combat v2, Convert_. Production never runs it: the game resets after the combat and valley reworks.
- **Reset raids and dungeons (2026-11-03):** _reset-raids-dungeons_ `{ confirm: "reset" }` (strict) wipes every raid and dungeon table of the **whole staging guild** in one transaction, to clear a tangled dev-clock history: every `raid_` table (weeks and everything keyed by week, the track, the ladder, the live finale rows, swap requests), `jackpot_pity`, every `dungeon_` table, and the raid posts queued for Discord. The tables are discovered from the schema by prefix, and a test pins the list so a new table is a visible decision. `raid_ladder` keeps its one row, with no rank. Creatures, talents, gear, balances, ledgers, the analytics log and the dev clock stay. The next request creates the week fresh (with `COMBAT_V2` on, a v2 week at track slot 1). The answer lists the rows deleted per table. Works with or without `COMBAT_V2`.
- **The raid test bench (2026-11-03, `combat/integration.md`, section 10):** Misa: "I just want to set up the board and run the fights. Then I want to reset and have the ability to do it all over again." Five tools (the fifth, _raid-seats_, is below), only with the `COMBAT_V2` flag on as well (staging; `404 not_found` otherwise), acting on the **whole staging guild**'s current raid week (the week the dev clock is in). They replace the phase jumps, the v1 resolve and simulate, the boss and tier setter, the Festival toggle, the roster filler, the live practice start and `raid-weekend`. Each bench step is one transaction and runs no scheduler event by itself.
  - _raid-clear_ `{}`: everything stored for the week (every table keyed by a week) is deleted and the week is created again by the normal path, so it is a fresh combat v2 week whatever it was (a v1 week becomes v2; a Festival week becomes a normal one): nothing placed, nothing fought, no done marker, and its **Boss Rank kept** (the week's own slot, so a week that was played to its end gets its rank back, and the track's slot, best share and failed weekends that its end moved are put back). Players' creatures, Knacks, talents, balances and what past weeks paid stay. Then **nothing may fire by itself**: if the game time is past the week's stage 1, the dev clock is moved back into the week's preparation (two days before stage 1, but never behind the real time: the offset is never negative); if the real time is already past stage 1, the clock cannot go back, so the events that are due are marked done (`outcome = skipped`) for the scheduler to leave alone and `raid-play` plays them. The answer says the rank and boss, whether the clock went back, the game time now and the events left for `raid-play`.
  - _raid-fill_ `{ count? }` (1 to 14; none means as many as fit): simulated players (`dev-guest-1` and up, the guests the Games' bots also use) that are not on the board yet each own six creatures with v2 talents and place their first three through the placement code (`Raid.place`: the first Knack their form knows, each in the lowest free slot, so they only ever take empty slots and never move what the caller placed). A guest takes whatever room is left, even fewer than three; the fill stops when a guest cannot place one. Refuses with `409 fought` once anything of the weekend has been fought, `409 clear_first` when the calendar is past an event that was not played here, `409 not_v2` on a v1 week. The answer says how many were added, how many are on the board and whether the board filled up.
  - _raid-rank_ `{ rank }` (1 to the number of slots in `raid-track.json`, 15 today): the week's slot, boss and rewards' rank and the server's track slot (best share and failed weekends start at zero for a new rank). A rank comes with its own boss (the track's order repeats). Placements that fall beyond the new boss's board move to the first free slot (or come off when none is free), as stage 1 does. Same refusals as the fill (`409 fought`: clear the board first).
  - _raid-seats_ `{ seats }` (1 to 8, or `null`: the default) **Creatures per player** (2026-11-06; Misa: "I have less testers than players so it could be cool to be able to override the number of creatures each player can bring to a raid"): how many creatures each player brings to the raid, instead of the boss's own piece (2 to 4). Kept for the guild in dev state (`g:raid_seats`; staging only), so it applies to the current week and every later week until it is set back to the default, and it stays through _raid-clear_. It enters through the arena (`arenaOf` in `raid-v2-core.ts`, the `seatOverride` of the week row that `Raid.week()` fills from the dev state): the placement cap, the board's width (`colsFor`: a piece of `seats` creatures is laid in columns of the boss's rows, so the board has `ceil(pieces x seats / rows)` columns, the spare piece included until stage 1), the view's `seats`, the spare column, stage 1's compaction, every stage's fight and its stored input (so the replays) read the same arena. The boss is sized for the **effective players**, `ceil(seats on the board / the boss's own seats per player)` (`effectivePlayers`: three testers bringing eight creatures against a three-seat piece fight what eight players would; with the default it is the real players, and it equals the board's width without the spare). _raid-fill_'s guests bring as many as the seats (they own twice the seats, at most one creature per line). The board is refitted when it is set (the earliest placed stay; a placement beyond the board moves to a free slot, as _raid-rank_ does). Refuses `409 fought` once anything of the weekend has been fought (clear the board first). The placement route's schema accepts slots up to 63 (production's limit, left alone), so a board wider than that (more than about six testers at eight seats) has slots that cannot be placed by hand.
  - _raid-play_ `{ stage: stage1 | stage2 | finale, live? }`: plays that fight now by the scheduler's own code (`Raid.playEventNow`, the same stage code `runDue` runs), without needing the calendar, and sets the done marker so the scheduler never plays it again. It refuses in plain codes: `409 already_played`, `409 play_stage1_first`, `409 play_stage2_first`, `409 boss_fell` (the boss already fell in an earlier stage), `409 nobody_placed` (stage 1 with an empty board), `409 nobody_left` (the creatures that fell stay out all weekend, so a small board can be wiped before stage 2: fill the board), `409 not_v2`. The finale plays to its end at once (`live` off): the week ends and the track moves or holds. With `live` (finale only) it starts the live fight now, for the live screen; the week ends when the fight settles. The answer carries `watch`: the week, the party (the caller's, or the first with a result) and the stage's name, which the panel opens as the replay at once (null for a live finale: the game's finale screen shows it).
  - _What the bench does not do_ (the old tools did): jump the week to a phase or toggle a Festival week, play a v1 week, run the live practice finale with a countdown, set the boss apart from the rank, set the simulated roster to an exact size (it only adds), and, between the stages, have the guests replace their fallen creatures from their spares and one guest ask for a swap. Use _Reset raids and dungeons_ and the clock for what is left.
- **The valley systems (2026-11-05, `valley/phase5-plan.md`, step 0):** _valley-fresh_ `{}` exists only when `VALLEY_SYSTEMS` is on as well (staging; it needs `VALLEY` and `COMBAT_V2` on), and acts on the **whole staging guild**. It wipes every player's progress (every table with a `user_id`, the players' dev state, and the valley's guild-level tables listed in `VALLEY_GUILD_TABLES` in `dev-tools-valley.ts`, none yet) and puts the dev clock back to real time, so each player starts at the starter choice on day 0. Players stay signed in. Production has the dev tools and the flag off, so the route is a 404 there.
- **Roster presets (2026-11-06):** _apply-roster-preset_ `{ preset, userId | everyone: true, confirm }` (strict) exists only with the `COMBAT_V2` flag on as well (staging; `404 not_found` otherwise). Misa: "give players a bunch of creatures according to some sensible presets and seed their bags with items. Then we could try the raid." It **replaces** a player's creatures and gear bag with a preset, and is the one dev tool that acts on a player other than the caller, so: the id must be a player of this guild (`404` otherwise; simulated guests `dev-guest-*` are never targets, with "everyone" either), and `confirm` must be the player's name (case and outer spaces ignored) or `everyone`, or the tool answers `409 confirm_mismatch` and changes nothing. With "everyone" it acts on the **whole staging guild**, each player once. It deletes the player's creatures and everything stored by creature id (every table with a `creature_id` column, found from the schema: talents, raid placements, explorer and crafting progress, Workshop jobs, Games entries and badges, the lounge's company), the player's line book and every item they own, then makes the preset's creatures by the normal creation path (`insertCreature`: quirk, v1 talent, the first v2 talent from the line's pool learned in slot 1; no Knack, so players pick one) and its items by `rollItem` (lines drawn from the pools by the server's live gear dice), worn by nobody. Balances and the ledger (append-only), parts, blueprints and the week's raid state are not touched. `GET /api/dev/players` lists the guild's players (with what they own) and the presets in numbers, for the panel's picker.
  - _The four presets_ (`apps/worker/src/dev-presets.ts`, data in one place; numbers copied from the lab's valley roster profile, kind `daily`, `packages/lab/data/valley/roster-profile.json`, with the gear model of `packages/lab/src/gear.ts`; the file's comment lists every pick). - **A target player (2026-11-13, Misa: "give target players pretty much everything"):** every tool that acts on one player's own data (`TARGETED_TOOLS` in `dev-schemas.ts`: Bait and Essence, parts, supplies, blueprints, creatures, explorer, familiarity, Crafting XP, gear, the bag, jobs, trips, push-on and night flags, slots, journal, the dungeon's per-player tools, and the four below) accepts an optional `userId` in its body (default: the caller). `DevTools.run` takes it off the body before the tool's strict schema sees it, checks it is a real player of this guild (`404 not_found` for a stranger and for a simulated `dev-guest-*` player, as for the presets), and runs the tool for that player; the analytics `dev_action` keeps the caller as actor. Never targeted: the clock, the raid bench, the Games, `dungeon-modifiers` and `dungeon-seed` (guild-wide), `reset-account`, and the roster presets (they name their own target and need the typed confirmation). Tools that name a creature (`creatureId`) find it among the **target's** creatures, so a creature of the caller is `404` for another target.
- **Give tools (2026-11-13):** all go through the game's own functions and are per-player (targeted):
  - _grant-creature_ `{ species, level?, fusion?, shiny?, count? }`: `count` 1 or 2 is how many creatures the player ends up with in that line (a line holds two: `line_slot` 1 and 2); a slot that has a creature becomes the species, an empty one gets a new creature (`insertCreature`).
  - _grant-gear_ `{ baseId?, slot?, rarity?, itemLevel?, count? }`: a base or a random one (of the slot, and of bases that exist at the item level), a rarity or a random one among common, rare and epic, an item level or the base's lowest (random for a random base), up to 50 items; `409 bag_full` and nothing given when the bag cannot hold them all.
  - _grant-currency_ `{ bait?, essence? }` (whole numbers from 1): adds through the ledger as source `dev`. _set-balances_ still sets an exact amount.
  - _grant-xp_ `{ creatureId, amount }` or `{ all: true, amount }`: through `awardExperience`, so levels stop at ribbons and evolutions; no analytics event.
  - _grant-talent_ `{ creatureId, talentId, slot? }` (`COMBAT_V2` on, else `404`): a talent of the creature's line pool (`400 wrong_line` otherwise) goes in the line's Talent Book and the creature learns it, and sits in `slot` when that slot is open at its level (`409 slot_closed`).
  - _set-knack_ `{ creatureId, knack | null }` (`COMBAT_V2` on): saves a Knack the creature's form knows (`409 knack_not_known`), or none.
  - Parts, supplies and blueprints (_grant-parts_, _grant-supplies_, _grant-blueprints_) and the roster presets were already grants; they sit under Give in the panel. `GET /api/dev/players` now also says who the caller is (`you`) and lists each player's creatures (`roster`), for the target picker and the creature pickers.
- **Logging:** every dev action is logged as an analytics event kind, `dev_action`, flagged so reports exclude it. Staging data is never mixed into production reports.

## The dev clock

A per-guild **time offset** is stored in the Durable Object on staging only. `now()` is the real time plus the offset, so time-based features can be fast-forwarded without special cases:

- expeditions and push-on goals;
- Workshop jobs;
- the 13:37 daily reset and the dungeon day;
- raid week phases.

A "+1 h, +6 h, +1 day, next 13:37, next phase" control moves it, and "reset clock" clears it. Alarms re-arm from the shifted clock.

## How to test with the dev panel

The panel exists only on staging (`creatures-staging.misacorp.dev`, whichever branch was last put on staging with the `deploy` workflow's manual run). Production has neither the routes nor the panel code.

1. Open the Activity on staging. A small orange **DEV** button sits at the bottom right. Tap it to open the panel (full screen on a desktop, a sheet on a phone); **Close** or Escape shuts it. Pick a section in the nav; the **Target player** at the top decides whom the Players and Game-systems tools act on (leave it on You for yourself).
2. The **Clock** section has the dev clock: it shows the game time, the game day, how far the clock is shifted and the raid week. Use +1 h, +6 h, +1 day, Next 13:37 or Next phase to move time forward (expeditions, jobs, the daily reset and raid phases follow). Reset clock puts it back to real time. The clock goes back only through Reset clock (and the raid's Clear the board, when it has to).
3. The section for the tab you are on opens first (Creatures, Workshop, Expeditions, Dungeon or Raid), else Give. Fill in a form and tap **Apply**; the result or the error code shows at the top of the panel, and the screen reloads so the change shows at once. A field left empty means "leave as it is".
4. **Give** gives the target player a creature (species, level, fusion, shiny, one or two), gear (a base or random, slot, rarity, item level, a count), Bait or Essence, parts, supplies, blueprints, XP for one creature or all, a talent (into the Talent Book and a slot) and a Knack; _Set Bait and Essence_ sets an exact amount.
5. **Build and account**: _Reset local flags_ makes the Raid tab's tag hint and the slot-wipe notice show again. _Reset my account_ deletes your data on this server (creatures, gear, trips, raid, dungeon, and so the welcome kit comes back); type `RESET` to enable it.
6. **Analytics** (Tools) lists the last 50 events this server wrote (dev actions are logged as `dev_action`) and has Roll up now.
7. **The raid test bench** (Raid section, staging runs combat v2): press Clear the board; place your creatures on the Raid tab; press Fill the empty spots (leave the number empty to fill the board); pick a Boss Rank and press Set if you want another boss; then press Play stage 1, Play stage 2 and Play the finale. Each opens its replay at once; its Back button returns to the game. Watch the finale live starts the finale live instead, for the live screen. A refusal says what to do ("Play stage 1 first", "The boss already fell"). To do it all again, press Clear the board.
8. **A playtest with a few testers** (Give, then the Raid section): pick the tester as the target player, then in _Give_ pick Week 2, 8, 16 or 24 under the roster preset, choose them (or Everyone), type the name (or `everyone`) and press _Replace creatures and bag_: their creatures and gear bag become the preset. In _Raid_ press Clear the board, set _Creatures per player_ (for example 8 with three testers, or Default), then let the testers place on the Raid tab; Play stage 1 and the rest as in step 7. Set _Creatures per player_ back to Default when the playtest is over.
9. The panel and every dev route are for server managers only (the owner, Administrator or Manage Server): a tester who opens the Activity on staging sees no DEV button.
10. Nothing else is needed: the panel uses your normal session. Most tools change your own player and your own server by default; pick another player of the same server as the target to act on them instead.

How the panel is kept out of production: `apps/activity/vite.config.ts` sets `__DEV_TOOLS_BUILD__` to true only for the dev server, tests and a build with `TARGET_ENV=staging` (the deploy job already sets that).
