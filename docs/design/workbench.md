# Component workbench (staging only)

Status: **built 2026-10-14**. Misa: "see every reusable UI component, learn its name, try its props, and give feedback so agents can iterate."

## What it is

A gallery of the game's reusable components, on its own page: `https://creatures-staging.misacorp.dev/workbench.html` (locally `pnpm dev`, then `/workbench.html`). It needs no Discord and no sign-in, uses fixture data only and makes no `/api` calls. It is home-grown, with no new dependency.

- **The list** groups components by kind: Bars, Tags & chips, Popovers, Slots, Loot & reveals, Headings & banners, Icons, Controls, Creatures & game pieces. A search box filters it.
- **A component page** shows its name as written in code, its file, a plain sentence saying what it is and where it appears, a live preview, **presets** ("Empty", "Half", "Festival"...), **controls** for its props (slider and number, select, toggle, text), a width switcher (360, 390, full) and a background switcher (the panel colours of the app).
- **The preview is an iframe** of the chosen width (`?frame=1` of the same page), so the game's media queries see a real phone-sized window and the layout is the one a phone gets. Interactive pieces really work (Popover, DungeonTeam and RaidBoard with picker and drag, ToggleButton, PlaybackControls, AbilityChip, glossary tags, SmallCreature).
- **The address holds the view**: `#c=<Name>&p=<changed props as JSON>&w=<width>&bg=<background>`. Copy it to share or bookmark a view. Props from an address are cleaned (unknown names, wrong types and out-of-range values are dropped).
- **Feedback**: "Give feedback" opens a prefilled GitHub issue (`Misacorp/creatures`, label `ui-feedback`, title `UI: <Name>`) with the component, file, changed props as JSON, width, the workbench link and a "What I'd like changed:" line. "Copy details" puts the same text on the clipboard for pasting into a Claude chat. No token, no API call: it is a plain link. An agent picks the issues up with the `ui-feedback` skill (`.claude/skills/ui-feedback/SKILL.md`).
- **DEV panel**: the "Component workbench" section shows the address, with Open (through the Discord SDK's `openExternalLink` inside Discord, a new tab elsewhere) and Copy link.

## Staging only

The workbench is a second Vite entry (`apps/activity/workbench.html`, code in `apps/activity/src/workbench/`). `vite.config.ts` adds it to the build inputs only when `__DEV_TOOLS_BUILD__` is true (dev serve and `TARGET_ENV=staging`), so a production build emits no `workbench.html`, no workbench script and no workbench styles. `src/dev-build.test.ts` builds both ways and checks the page, a marker string (`WORKBENCH_MARKER_5c1e`) and a stylesheet class. If someone opened `/workbench.html` on production, the Worker's single-page-app fallback would serve the game's `index.html` (harmless; `wrangler.jsonc` is unchanged). Staging serves it as a static asset, since only `/api/*` runs the Worker first.

## How to add a component

1. Write an entry in the file of its group under `apps/activity/src/workbench/entries/` (`bars.tsx`, `tags.tsx`, `popovers.tsx`, `slots.tsx`, `loot.tsx`, `headings.tsx`, `icons.tsx`, `controls.tsx`, `creatures.tsx`). An entry has: `name` (the exported component name), `file`, `group`, a one-sentence `description`, `controls` (one per prop to edit), `defaults` (a value for every control), `presets` and `render(props)`. Read props with `num`, `str` and `bool` from `props.ts`; use fixture data from `data.ts`. A component that holds state (open or closed, selected) gets a small wrapper component in the same file.
2. If the entry is new, it is already in the list: each group's array is in `registry.ts`.
3. `registry.test.ts` fails when a component exported from `src/ui/*.tsx` has no entry (use `covers` for a helper shown on another page), when a default does not fit its control, or when a preset names a prop that does not exist. A hook or helper that is not a component goes in the test's `NOT_COMPONENTS` list.
4. Render text as text only, with no inline `style=` attributes (use classes or `cssVars`).

## Reproducing a bug in a real browser

For a timing or gesture bug (a tap lost after a drawer closes, a long press), load the real component in Chromium with phone emulation:

- **A component with an entry:** open `workbench.html?frame=1#c=<Name>&p=<props>` from a Playwright script in your scratchpad. `scripts/shoot.mjs` shows how to start Vite and launch the preinstalled Chromium.
- **A whole screen with no entry** (`Workshop` and the others under "Not covered"): write a throwaway page in `apps/activity/scratch/`. It is gitignored and lint skips it, and `pnpm dev` serves it at `/scratch/<page>.html`. It can import from `../src/` and the test samples (`creature-card-sample.ts`). Never put probe files anywhere else in the repo.
- Chromium is not Discord's phone app: a bug that only shows on the phone (Misa's drawer pull, retro 2026-10-28) may need his answers on how and where it happens. Ask those before guessing.
- If a step is denied, stop and ask Misa. Don't do the same thing another way.

## UI audit

`apps/activity/scripts/ui-audit.mjs` finds layout overflow on every workbench page. Run it from `apps/activity`:

```
node scripts/ui-audit.mjs [--only <entry name substring>] [--widths 360,1100]
```

It starts its own Vite server and the preinstalled Chromium (like the font audit; `PLAYWRIGHT_PATH` and `CHROME` override the defaults), reads the entry list from `registry.ts` and opens every entry and every preset at 320, 360, 390, 412, 768 and 1100 px (a real window per width). A new entry or preset is audited with no change to the script. A full run opens about 1,150 pages at six widths and takes about 25 minutes (three widths at a time); use `--only` while working on one component.

It reports, per page and width: (a) the page scrolls sideways; (b) an element sticks out of its nearest clipping ancestor's content box, is cut off vertically by a clipping box, or shows past the viewport; (c) text spills out of its own box (unless the box truncates with an ellipsis); (d) anything steps out of the card's content box. Output is one line per page and width ("clean" or the findings with the overshoot in px), then `AUDIT CLEAN` (exit 0) or `AUDIT FAILED (n)` (exit 1).

A deliberate crop (a strip of a scene, bunting cut at the card's edge, a scene canvas's inside) is marked `data-audit-clip` in the markup: everything inside it is skipped, and the marked box itself is still checked. Never put it on text. `GAMES_STATES` in the script lists Valley Games states that need a tap (picker open, favour popovers, replay); they run when the `--only` filter matches their entry.

### Overlay spacing audit

`apps/activity/scripts/overlay-audit.mjs` (`node scripts/overlay-audit.mjs [--kind popover|drawer|sheet|all] [--only <entry>] [--width 390]`; `popover-audit.mjs` is a thin wrapper for `--kind popover`) checks the spacing of every popover, drawer and sheet the workbench can show against the scale of its kind (`ux-patterns.md`, "Spacing inside a popover" and "Spacing inside a drawer or sheet").

- **Popovers:** opens every entry with its default props, taps each kind of popover trigger (`aria-haspopup="dialog"`, one per class name) and checks: (a) a button or action row at least 8px under the block above it; (b) the stacks' children a scale step apart; (c) no extra space inside the padding at the top or the bottom.
- **Drawers and sheets:** opens the entries listed in `OVERLAY_ENTRIES` (the ones that can draw one; add yours there) with their defaults and every preset (most presets draw the drawer open; an entry whose default view shows none gets its buttons tapped). Checks: (a) a button or action row at least `--dr-action` under the block above it, in a body and in a footer; (b) the children of the stacks (`.drawer-body`, `.drawer-toolbar`, `.drawer-footer`, `.dr-stack`, `.sheet`) one step apart, the groups (`.dr-group`) the tight step; (c) the body and the footer start and end at their own padding; (d) nothing sticks out of the stack's left or right edge; (e) no part has a vertical margin of its own (an item frame's ring and what an accordion holds aside).

A full run (all kinds) checks about 170 popovers, 145 drawers and 9 sheets in about six minutes; Chromium is relaunched every 10 entries. Output and exit code as the UI audit's. It is not in CI (no browser there); `ui/popover-spacing.test.ts` and `ui/drawer-spacing.test.ts` keep the CSS rules in CI.

## Game screens and looks (2026-10-28)

`GameScreens` draws every main screen in the game's real frame (`src/AppFrame.tsx`, shared with `Game`) on fixture data, under a look (`src/looks.ts`, `data-look` on the root). `workbench.html?frame=1&bare=1#c=GameScreens` renders it straight into the page (no stage) so media queries and fixed bars behave as in the game. `node scripts/screens.mjs --out <dir> [--looks ..] [--screens ..] [--sizes phone,desktop,hd]` shoots all of it and writes per-look contact sheets and per-screen comparisons. The Raid tab is composed by hand (timeline, boss card, roster) because the real `Raid` loads from the server.
