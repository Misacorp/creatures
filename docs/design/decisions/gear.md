## 2026-10-31: Gear in combat v2: talents lead early, a balance mid-game, gear leads the endgame; no slot level requirements; gear alone can build crit **[Misa]**

ID: `2026-10-31-gear-in-combat-v2-talents-lead` · Status: current

**Decision (Misa, answering `docs/design/combat/gear-plan.md` questions 11 to 13, 2026-10-31).**

- **Gear's weight grows with the game.** Early on a talent is worth more than gear (gear is rare and weak); in the mid game the two balance; in the endgame gear is the main way to grow, and chasing the highest-tier lines is rewarded. The gear plan's budget per piece rises with item level so that a typical set passes a good talent's worth in the endgame, rather than being held at "about one talent" throughout.
- **No slot level requirements.** Hat, Scarf and Charm all open at creature level 1 (today Scarf 7 and Charm 13, `RULES.gear.slotUnlockLevel`). The change lands with combat v2's port, not in the shipped game now.
- **Gear alone can build a crit creature** (about +20% damage from two chance lines and a damage line), and it is strongest together with the crit talents.

**Reasoning.** Misa: "In the endgame the gear is the main way to go. Players will have access to the highest tier modifier lines on gear and should be rewarded for chasing those... In the beginning of the game a talent will be worth more power, as gear is less common and powerful. In the mid game there ought to be a balance of both." The valley's players level fast (a daily player's best creature is level 13 or more by week 2), so the slot levels only locked the 10th to 20th creatures out of gear. On crit: "It'll always be more meaningful when combined with the right talents though."

## 2026-10-31: [Misa] Items with no element get an oat-beige coat instead of grey

ID: `2026-10-31-items-with-no-element-get-an` · Status: current · Amends: `2026-10-30-every-named-item-has-its-own`

**Decision.** Misa (2026-10-31): neutral items "are quite bland and gray. Would it be possible to give them a coat of paint of their own? It can still be low in saturation, but ... light beige or brownish. Not to be confused with the tones of mire." An item with no element tint and no set (the neutral pieces, and the role and explorer charms such as Warden's Bell and Crossroads Compass, which were grey for the same reason) is drawn in `NEUTRAL_PAINT` (`apps/activity/src/gear-sprites.ts`): `t #bba88c`, `u #7f6e58`, `h #e4d8c2`, an oat beige. The sprites keep their grey base palette, so the paint is the tint like any element's. A test keeps it low in saturation, in the beige-to-brown hues, and apart from every element and set colour.

**Reasoning.** Three beiges were compared beside Mire and the explorer set (the two nearest browns): a pale linen, this oat, and a grey driftwood. Oat reads as beige-brown at a glance, while Mire stays a saturated ochre and the explorer set a brighter golden tan. The role charms take the same coat: leaving them grey would keep the bland look Misa pointed at, and a role's own colour belongs to its set.

## 2026-10-31: [Misa] Element versions of a shared item get a small element flair

ID: `2026-10-31-element-versions-of-a-shared-item` · Status: current · Amends: `2026-10-30-every-named-item-has-its-own`

**Decision.** Misa (2026-10-31): "Could we add some small flair to the Trail charm and the items that are the same shape? Spark one a bit spiky, grove one with vines, you know." Each element version of a shared look gets a small overlay (`ITEM_FLAIR` in `apps/activity/src/sprites/data/item-flair.ts`, by look id and element), drawn over the shared sprite by `withFlair` in `itemArt`: Spark spikes, Grove a vine or leaf, Tide a drop or shell, Ember a flame flick, Mire a mud drip or reed. The neutral version stays plain; set pieces and items with a look of their own get none. The overlay's `t`, `u` and `h` are still tinted by the element. `gear-sprites.test.ts` requires a flair for every element version of a shared look and none elsewhere, each visible and passing the item lint.

**Reasoning.** Element versions keep one shape (Misa's earlier rule: same stats, same sprite), so a set still reads as one item, while the touch makes each element recognisable without colour alone, which also helps colour-blind players. An overlay rather than a second full sprite keeps the shape in one place: a change to the shared sprite carries to every version.

## 2026-10-30: [Misa] Every named item has its own sprite; element versions share one, tinted

ID: `2026-10-30-every-named-item-has-its-own` · Status: current, amended by `2026-10-31-element-versions-of-a-shared-item`, `2026-10-31-items-with-no-element-get-an`

**Decision.** Misa (2026-10-30): "Each item with a unique name should have a unique sprite. If items have identical stats but they're just a different element version, then let's just use the color tint that exists today." An item base is drawn with its **look** (`itemLookId` in `apps/activity/src/gear-sprites.ts`): two bases share a look when they are the same slot, have the same stats, neither is a set piece, and each is neutral or an element (so a role or explorer charm, or a set piece, always has its own). The first base in content order names the look; the others wear its sprite in their element's tint, as before. With today's content that is 60 looks for 77 items (for example Trail Cap and Kelp Cap share one; Wayfarer's Hood and Tidecaller's Crown share one because their stats are identical). The sprites live in `src/sprites/data/item-{hat,scarf,charm}-sprites.ts`, drawn in the neutral greys `t`/`u`/`h` that the tint swaps; set pieces keep the gold trim (`g`, `w`) and their set tag's tint. The old six shared sprites stay as the fallback for a base drawn before its own sprite. `pnpm art items` draws every item as the game does, labelled by name, plus a card per look with each tinted version.

**Reasoning.** The rule is computed, not listed, so a new element version of an item shares its sibling's sprite with no art work, and a new item with its own stats shows up as a missing sprite in the tests. Keying shared looks on identical stats is Misa's wording; it pairs a few names that are not obviously one item (the hood and the crown), and those sprites are drawn to read as both.

## 2026-10-27: Marked items, dismantled as a pile

ID: `2026-10-27-marked-items-dismantled-as-a-pile` · Status: current, amended by `2026-10-27-bulk-selection-replaces-marking` · Amends: `2026-10-16-gear-b-built-reach-dismantle-jobs`, `2026-10-16-misa-agrees-with-the-podcast-s`, `2026-10-21-the-workshop-s-supply-jobs-are`

A player asked for a quick way to clear items past the 60-item bag. Misa's rules: mark items, then one free creature dismantles the whole marked pile at once; worn items and items in an open job cannot be marked; equipping a marked item clears its mark; the request names the exact items the confirmation showed (409 and nothing taken if the marked set changed); the creature must be free (not away, not on a job); it gains Crafting XP but no creature experience; Market Day's bonus goes to the most valuable items; the old timed dismantle job goes.

1. **Marks.** Migration 48 adds `gear_items.dismantle_mark` (read with the bag, no index) and `dismantle_days (user_id, day_start, items)`. `POST /api/gear/mark { itemIds (1 to 60), marked }`: all or nothing, 409 `item_worn` / `item_in_job`, unmarking always works, no key (repeats are harmless). Equip and Equip best clear the mark in their own transaction. `GearItemView.markedForDismantle`; the item picker's tiles and detail card show it.
2. **The pile.** `POST /api/gear/dismantle { creatureId, itemIds, idempotencyKey }`, one keyed transaction (`gear_actions`, kind `dismantle_pile`). Marked set not exactly `itemIds` is 409 `marks_changed`; busy creature is 409 `creature_away` / `creature_on_job`. It takes no Workshop slot. The preview is `POST /api/workshop/preview { kind: 'dismantle', ... }` for a pile (range, Crafting XP, blueprint chance, `boosted`, `tinkersLuckBp`; no time).
3. **Rolls (rules unchanged, now per item).** Refund from `rollDismantle` (not by Crafting level), blueprint draw 6% + 1 point per Crafting level of the dismantler, the dismantler's Tinker's luck, Essence once through the ledger (`dismantle-pile:<key>`), all live server RNG, items rolled most valuable first.
4. **Crafting XP.** The total the old timed jobs paid: 6 per 5 Commons (a bundle), 12 per Rare, 24 per Epic (`pileDismantleXp`); Apprentice adds its share once on the total. No creature experience.
5. **Market Day** boosts the day's first 2 dismantled _items_ (not jobs): the pile is ordered by rarity, then item level (`pileOrder`) and the first `dismantleBoostLeft` items roll the top of their range. Old timed jobs started today count one each; piles count in `dismantle_days`.
6. **Replaced from 2026-10-16.** Starting a `dismantle` job is 410 `dismantle_job_removed`; running jobs finish and claim as before (their claim code is kept). The item drawer's per-item Dismantle wizard became "Mark for dismantling" / "Unmark"; the bundle rules (5 Commons, no mixing) no longer apply to new dismantles.
7. **UI.** "Select many": "Dismantle items" in the Gear section starts a selection mode (taps toggle, a small "i" on each tile opens the card, presets All Common / Below level 10 / Clear, a bar with the count and Dismantle), then the shared wizard in a drawer (Who dismantles, then "Dismantle 23 items (20 Common, 3 Rare)?"), then the existing job results card for the whole pile. Taps show at once and requests go out one at a time (`use-marks.ts`).

## 2026-10-21: the Workshop's supply jobs are one wizard in a drawer; level limits may fold in job pickers

ID: `2026-10-21-the-workshop-s-supply-jobs-are` · Status: current, amended by `2026-10-27-marked-items-dismantled-as-a-pile` · Amends: `2026-10-20-the-workshop-s-supplies-become-one`

Craft, Refine and Recycle on the supply card now open one drawer, `JobDrawer`, built on the shared Wizard (`ui/Wizard`). The recipe (in, arrow, out, time) sits once at the top, pinned in the drawer's toolbar slot, and the "?" help is beside the title. Step 1, Who crafts: creatures who can do the job first (best crafter first, each with its time), busy ones at the level greyed with "On a job" / "Away on a trip", and the creatures under the job's Crafting level folded into one greyed row ("4 more creatures need Crafting level 3") that expands on a tap. Step 2, Ready: who and their time, and the treat box. The footer is the gold start ("Craft", "Start refine", "Start recycle", with the Bait badge for a packed treat) and always says why it is off. Back on Who and Escape on Who close the drawer; Escape elsewhere goes one step back. The start call is the same as before (same request, same idempotency key). A failed start keeps the drawer open and shows the server's error in the footer: the game's own error line sits behind the drawer, so `Game` passes its `error` down through `Workshop` and `SupplyCrafting`, and the drawer shows it only after its own start failed.

This is an exception to "pick lists show everyone" (ux-patterns.md): under-level creatures are folded, not listed one by one, because a Workshop roster is long and most of it is under level 3 for a good while. They are still one tap away, and busy ones are never hidden. The old silent grey Start (everyone at the level busy, a lower one free) is gone: with nobody who can do it the footer says "Nobody free has Crafting level 3.", or the slot and stock reasons the start check already had. `JobStarter` (the old inline panel) had no other user and was removed; gear crafting followed on 2026-10-22 (below).

- **The fold row is a quiet divider, `ui/FoldRow`.** It is not a boxed pick row and has no chevron (the first version's was oversized): the label is small, muted and centred, with long pixel dashes (4 units, a gap of 2) running out to both edges, so it reads as a divider. Open or closed is `aria-expanded`, and the revealed rows are the other cue. It is still a real button with a 44 px tall hit area and the app's focus ring. Generic on purpose (label, open, toggle, the id of what it folds), so other lists can use it.

The Wizard itself needed no change: the recipe fits the Drawer's existing toolbar slot, the error fits the footer's `extra` slot, and `initial` and `onExit` covered the start step and "Back closes". `PickRow` was split out of `CreaturePicker` so the job step and the gear pickers share one row.

- **Gear crafting uses the same drawer (2026-10-22).** Craft on a blueprint card opens `JobDrawer` (`craft-job.ts` builds the job); `CraftStarter` is gone. The pinned recipe is the plain craft's parts for the best crafter, as the card lists them, and the Kelp Cap as the output. Steps: Who crafts (the blueprint's own `needsCraftingLevel`, under-level creatures folded), **How hard do you reach?** (plain, Rare, Epic with the server's odds, time and cost for the picked creature via `useJobPreview`; Details has item level and step-up chance), Ready (who, the final time, the chosen reach, the treat). `useJobWizard` gained an optional `spec.craft`: it adds the Reach step, loads the preview, takes the cost, Essence and time from the chosen reach and puts `reach` on the request; supply jobs are unchanged (their request carries `reach: 'none'`, ignored). Past Who the footer says "Loading the odds..." or "The odds did not load. Go back and pick again." instead of a silent grey button; a reach that costs more Essence or parts than held is selectable and the footer says what is short. Decision: no `BagFullNote` on Ready. A craft with a full bag cannot start, so the footer's existing "The bag is full." blocks from the first step (the wizard cannot reach Ready), and the note's "gear you find becomes parts" would be misleading there.
- **Dismantling is a wizard too (2026-10-22).** The Workshop item drawer's Dismantle opens `DismantleWizard` (replaces `DismantlePanel`) as a drill-in in the place of the item, never a second drawer. Step 1, Who dismantles, is the job wizard's `JobWhoStep` (free creatures first with their time, busy greyed with the reason; it got `legend` and `groupName` props, defaults unchanged). Dismantling has no Crafting level rule, so `jobWho` runs with minimum 0 and nothing is folded; a dismantle job takes no treat. Step 2 is the confirmation: the worker with the server's time, the yields as badges, the blueprint chance, "Comes off X first", and "Cannot be undone." above the gold "Dismantle". The server preview is asked only when step 2 opens. Back and Escape are the safe exit (from step 1 back to the item, with the Dismantle button focused). The old "Keep it" button is gone; instead the focus moves to Back when the confirmation opens, so a second Enter on the button that said "Next" cannot dismantle. The request and idempotency key are unchanged and success behaves as before (the item leaves, the job appears). A refused start now keeps the confirmation up and shows the server's error there (before, the panel just closed): `Game` passes `error` through `Workshop` to `ItemDetail`. Flipping pauses while the wizard is shown, like Equip on. The gold button is sticky at the bottom of the drawer body, because the item drawer has no footer slot.

## 2026-10-21: A found item opens its item card (tap, or hover with a mouse)

ID: `2026-10-21-a-found-item-opens-its-item` · Status: current

Misa asked to inspect an item where it is found, ideally on hover on a computer.

- **`FindItem` does it itself**, so every screen that pays gear gets it (dungeon end screen, trip result, raid summary, other grants via `LootList`). The row becomes one button that opens the full `ItemCard` in the shared page popover (`host.openCustom`). Tap and Enter/Space open it, a second tap or Escape closes it. Hover (a mouse or pen, and only when `(hover: hover) and (pointer: fine)` matches) opens it and leaving closes it; a click while it is open from hover pins it. A hover never replaces another open popover.
- **Where the data comes from.** A grant's gear carries only base, rarity and level; the card's stats and lines are the server's and are not worked out in the client. `Game` therefore provides the gear view's items as `GearItemsContext`, and `FindItem` takes an optional `id` and looks the item up. No id (a boss chest's banked gear on the descent card and node drawer), the gear view not loaded yet, or the item since dismantled: the row stays plain, as before, with its badges tappable.
- **Badges inside the button are plain** (not tappable), as in the gear list, so no button sits inside a button. The card's own badges are plain too.
- **An Equip button** (Misa, 2026-10-21) sits centred under the card in that popover, as wide as its label. It closes the popover and opens the creature sheet (`RosterPicker`, opened from a page, which the rule allows) with the Workshop's "Equip on" rows (`equipOptions`), and a pick sends the Workshop's equip action (`gearActions.equip`, server decides). `Game` provides it as `EquipContext` through `EquipHost` (`equip-from-card.tsx`), which also draws the sheet; without creatures or outside a host there is no button. The Workshop drawer does not show it (it has its own drill-in). So a mouse can reach the button, a hover-opened popover now closes 200 ms after the mouse leaves the row, unless it has entered the popover.

## 2026-10-20: Workshop conversions, Refine and Recycle

ID: `2026-10-20-workshop-conversions-refine-and-recycle` · Status: current, amended by `2026-10-20-the-workshop-s-supplies-become-one`

Misa: players can turn expedition supplies into other things in the Workshop, as timed jobs like dismantling.

- **Recipes are data.** `packages/game/src/content/data/conversions.json`, validated by `content/conversion-schema.ts` at module load (like supplies and destinations). A recipe is `{ id, kind, inputs, outputs, hours, craftingLevel }`; an input or output is `{ type: 'supply' | 'part', id, amount }`. Recipes name supplies by id only, never by effect, so supply numbers can change freely, and a later currency adds recipes (and, if needed, a new ingredient `type`) without engine changes. The file is explicit (16 recipes) rather than generated at load: it is easy to read and tune, and the loader checks the rules below so a typo cannot ship. Amounts are fixed integers (no ranges): a recycle is deterministic, so the screen can show exactly what comes back.
- **Refine** (8 recipes): 3 supplies of one kind and tier into 1 of the same kind, next tier (basic to good, good to great), lures included (a lure uses no Bait to refine). 2 hours for basic to good, 4 hours for good to great. It needs the Crafting level of the supply it makes (3 for good, 5 for great, from the supply's blueprint). The loader rejects a refine that does not make exactly one supply of the same kind one tier up, or that takes fewer than 2.
- **Recycle** (8 recipes: every good and great supply, none for basic): 1 supply gives back parts only, never Bait (a lure recycles to scrap only). Each part is under half of what crafting the supply cost, part by part (cost 4 gives 1, cost 7 gives 3, cost 3 gives 1, cost 1 gives 0), so crafting, recycling and refining can never make parts from nothing. Basic supplies cost 2 scrap, so half is already 1: they have no recycle recipe (it would be 50%, or nothing). 1 hour for good, 2 hours for great, Crafting level 1. The loader enforces "less than half, parts only, same supply".
- **Pure rules** in `rules/conversions.ts`: `conversionBlock` (level, then supplies, then parts), `conversionJobMs` (the same Crafting level reduction as `supplyJobMs`, 3% a level; Busy paws and the day's weather are applied by the server on top, as for supplies), `conversionXp` (nominal hours times `RULES.gear.skill.xpPerHour`; creature experience follows the nominal hours too).
- **Server.** A new Workshop job kind `convert` (`JOB_KINDS`), one for both refine and recycle: the recipe id in the job says which. Migration 36 (`workshop-convert-migration.ts`) rebuilds `workshop_jobs` to widen the kind CHECK (same pattern as 29: every row, column and index kept). The start request is strict (`{ kind: 'convert', creatureId, recipeId, treat?, idempotencyKey }`, unknown keys and recipe ids rejected); the request names only the recipe, never amounts. Starting takes the supplies and parts in the same transaction as the job under the client's idempotency key (the usual `runKeyed` of Workshop starts), uses a Workshop slot and a free creature, and refuses with `skill_too_low`, `insufficient_supplies` or `insufficient_parts` (nothing is taken). The job stores the recipe's resolved inputs and outputs, so the claim pays exactly what was shown even if the data changes meanwhile; claiming again returns the stored result and grants nothing. No randomness is involved. Analytics: the usual `job_start` and `job_claim` events with `job: 'convert'`, the first input supply as `base` and its tier as `rarity`, hours and Crafting level (ids and numbers only).
- **Client.** `ui/RecipeCard` is the general "combine things" component (inputs with have / need as count badges, arrow, outputs, a time badge, a reason and one button; it knows nothing of supplies); `ConversionCrafting` uses it in the Workshop's supply section for Refine and Recycle, listing only recipes whose supply the player holds. Start opens the same creature picker as other Workshop jobs. Job slots read "Refine Plain Lure" and "Recycle Sweet Lure"; the claimed job shows what went in, an arrow and what came out as count badges.
- **Words:** "Refine" for the upgrade and "Recycle" for parts back (compendium `items.md`, glossary entry `job-convert`).
- **Open:** the numbers (3 to 1, the hours, "less than half") are a first pass for Misa to tune in the data file; basic supplies cannot be recycled.

## 2026-10-18: Chance lines and trigger lines

ID: `2026-10-18-chance-lines-and-trigger-lines` · Status: current

Builds sections 6.3 and 6.4 of `gear-and-creatures-v2.md`. Technical decisions by the implementer, for the lead's review. No migration (a line is content and a stored item keeps its line ids and tiers), no change to `RULES`, no raid or dungeon number tuned (another branch reworks the dungeon). The engine reference is `combat-rules.md` sections 11 (chance) and 12 (trigger).

**What shipped.** 21 new lines, all special (an item has at most one special line: position, chance or trigger, through the same `rollLines` rule) and all **Rare and up**: nine **chance** lines (Second wind, Echo, Sidestep, Quick re-mark, Steady paws, Spill-over, Warm heart, Tinker's luck, Second look; Quick re-mark and Spill-over fell out of the mark code, so they are in) and twelve **trigger** lines (Payback, Kindling, Opening mark, Rally cry, Ember tail, Storm warning, Stubborn, Last stand, Overflow, Second breath, Patient, Shared warmth; the four optional ones fit cleanly, so all twelve are in). New line groups `chance` and `trigger` (both in `SPECIAL_GROUPS`), a new line unit `chance` (a card reads "Echo 8%", not "+8%"), and the loader checks that the group, the unit and the effect belong together (a chance above 100% is refused).

**Rarity, weights, worth.** "Rare and up" because a Common has one line and the design says these feel like Rare lines; a Rare or an Epic rolls one about a quarter of the time (a test checks it is between 10 and 45%). Stubborn is an Epic line from item level 12 with one value (like Lingering and Unbothered); Opening mark is a Rare line with one value. Weights lean the slots where the design says who wants it (Echo and Ember tail on Hats, Payback, Last stand and Sidestep on Scarves, Kindling and Warm heart on Charms) and sum to about 5 to 8% of a slot's pool for each of the chance and trigger kinds, so with the position lines (15 to 18%) a Rare or Epic's first line is special about a third of the time. The three Festival pieces each got one chance line in their narrow pool (Hearth Scarf: Second wind, Lantern Charm: Warm heart, Lantern Cap: Echo), so the +2 points of a Festival piece means something. `worth` is set so Equip best does not over-value them: a tier V line is worth under 4% of the wearer's power and never more than a 5 point crit chance (tier V chance lines 1.2 to 2%, triggers 0.5 to 2%, Stubborn 2%); a test checks both. The lines that fit a role carry `roles` (Payback, Last stand, Warm heart and Shared warmth: Guard; Kindling: Support; Opening mark: Setter; Echo, Ember tail, Overflow, Spill-over: Payoff), which only decides what a role-locked Charm rolls and who counts as "meant for" in Equip best; nothing is restricted.

**Values.** Chance is 4 / 6 / 8 / 10 / 12% at tiers I to V, **+2 points on an Epic or a Festival piece**. The bonus is worked out where the card and the fold read the line (`lineBonus` in `itemLines`, from the item's rarity and base), so a stored item needs no change and the card and the sheet agree. What a chance line does when it fires is not tiered and lives in code (`CHANCE_FX`: Second wind 5% of max HP, Echo 30% of the plain hit, Warm heart a 10% boost); a different size would be a new line, because it would change how a stored fight with that line replays. Trigger values are the design's number at tier V and about 25 / 40 / 60 / 80% of it below; Kindling is 40% at tier V (not the table's "a boost") because it works only on the first hit, where a Support's 15% works every round.

**The luck die.** A fight draws luck dice **only when some creature of it carries a chance line** (`hasChance`), and then `LUCK_DICE` = 10 per creature per round, uniform in [0, 10000), as the very last dice of the round (after crits, boss crits, the random target, the patterns, the Guard roll and the extra attacks' crits), so a fight without a chance line draws exactly what it always drew (the replay fixture is untouched, and a test replays 24 random fights with absent, empty and zero fields byte for byte and counts the draws). One die per kind of decision, numbered so one line never moves another's: 0 Second wind, 1 Echo, 2 Steady paws, 3 Warm heart, 4 Quick re-mark, 5 Spill-over, 6 to 9 Sidestep (the 1st to 4th area hit that creature meets in a round, the 4th for any after). All come from the fight's injected RNG (a seeded one in tests and the sim, the server's `crypto.getRandomValues` seed live); `Math.random` is not used. Round 1's other dice are identical with or without the line (a test); later rounds shift by the luck dice, as the Guard die has always shifted them.

**Chance lines in the fight.** Second wind: at round start, 5% of max HP (`healReceivedBp` applies, never above what is missing; nothing is written when nothing was missing), as a `heal` event with `cause: second_wind`. Echo: after a turn hit (not an ability's strike), if the boss still stands, the hit lands again for 30% of its **plain** damage (the reaction bonus is not repeated; no mark, reaction or crit), counted down to the phase floor like any hit (a `proc` event with the boss's HP; it can retreat the boss). Sidestep: an area hit that would reach the creature deals nothing, before Shield Wall, armor and cover (a `boss_hit` with `damage: 0` and `sidestep`); aimed and reflected hits are never sidestepped (so Bramble Season's reflect still lands). Steady paws: a silence the boss's move would put on it is shrugged off, after Unbothered. Warm heart: at round start, the living neighbour with the most Attack (ties to the lower slot) gets a 10% boost on its next hit. Quick re-mark: a non-Setter's hit on a boss with a mark of another element (not sealed) replaces it as a Setter's would. Spill-over: a reaction the creature sets off (not a reflected one) leaves its own mark, the chance version of Ridge Copper's `chainMark` (with both, Spill-over does nothing).

**Trigger lines in the fight.** All write a `proc` event; "next hit" is the creature's next **turn** hit (an ability's strike neither gets nor spends it, like `firstHitBp`). Payback: a creature that takes a hit meant for a neighbour (a Guard step-in, a reflected hit included, a Shield Wall that stops it included) and stands afterwards. Kindling: round 1, each living neighbour starts with a boost on its first hit (each dungeon room is a fresh round 1). Opening mark: round 1, the boss has no mark, the first creature in slot order with the line marks before anyone acts. Rally cry: a neighbour is knocked out (from any cause), all its hits deal more for the fight, once per fallen neighbour. Ember tail: a crit (turn or strike) gives the next turn hit a bonus. Storm warning: marked by a charge announcement, it takes less from that landing (splash included, not the plain attack of the same round). Stubborn: the first hit that would knock it out leaves it at 1 HP; the hit still shows its full damage and carries `stubborn`, the HP lost is what it really lost, and a Bramble Season or Backdraft reflect is a hit like any other (a test). Last stand: a hit leaves it standing at a quarter of its max HP or less (also when it started the fight below that), once, then it takes less from every hit. Overflow: it sets off a reaction, the next living creature in the round's turn order gets a boost on its next hit (nobody when it acts last; for an ability's strike at round start, the first in the order). Second breath: the first enrage round starts, it heals. Patient: a silence lands on it (not one it shrugged off or ignored), its next turn hit after the lost turn deals more. Shared warmth: a Support's Mend really heals it, that Support's next boost is bigger (it waits until the Support next boosts). The boosts the lines give go in the same list as a Support's, kept apart by a tag (a Support replaces its own boost each round, never one of these), are counted in `bonusBp` and credited as support credit to the creature whose line gave them.

**Tinker's luck and Second look (the two out-of-combat chance lines).** Both read the worn gear at the claim, like Apprentice and Lucky find, and use the server's live randomness. **Craft cost** means the plain craft's parts for the base and item level (`craftCost`: scrap by item level, plus one shard of the base's element for an element base; not a Reach's glimmer, shards or Essence, which the item does not remember). Tinker's luck: for each item of a dismantle job the wearer runs, with the chance, each kind of part is lifted to the craft cost when the ranges gave less (glimmer and Essence stay as rolled); one extra die per item, after that item's other draws and only when the worker has the line. The claim result says how many items it refunded (`tinkered`) and the job reveal says so. Second look: a **duplicate** the explorer's trip brings rolls its talent twice (one die for the chance, then a second roll) and keeps the better, where **better** is `talentScore` (the same worth Equip best and Recommended use) for the player's creature of that line (the first one, if they Kept two); a tie keeps the first roll. The trip result badges the catch "Second look". A Festival duplicate has no explorer, so it never has one. Both are stored with the claim's result, so a retry or a race returns the stored result and rolls nothing (worker tests through the real routes, with concurrent claims).

**The client.** The item card needed no change: it lists each line's server text with its number ("Echo 8%", "Payback +30%", "Stubborn") and tier pips, and every line opens its generated glossary entry (the line's `about` words, under 80 characters, section `gear`); two fixed entries, `gear-chance` and `gear-trigger`, explain the kinds (and `gear-position` now says the three kinds are special). The fight log reads every new event (`describeEvent`; a `proc` is a visible beat for the pacing); the stage floats a word over the creature whose line fired, a "+N%" over a creature that got a boost, the damage of an Echo over the boss, "SIDESTEP" (no flash, no shake) and green numbers for the heals; the replay moves the boss's HP for an Echo and the creatures' HP for a Stubborn hit and the heals, which a test checks against ten real engine fights with every line on (every creature ends with the engine's HP, the boss with its own). The client accepts the `proc` event type. Workbench: ItemCard presets "A Hat with a chance line (Echo, Epic: +2 pt)" (`trail-cap`, epic, item level 15, lines `echo:4,crit-damage:3,attack-local-pct:2`), "A Charm with a trigger line (Payback)" (`cinder-charm`, rare, 15, `payback:4,hp:3`), "A Scarf with a once-a-fight trigger line (Stubborn)" (`woolen-wrap`, epic, 15, `stubborn:1,area-ward:3,hp-local-pct:2`), "A Charm for the Workshop (Tinker's luck)" and "A Festival piece with a chance line (Second wind, +2 pt)"; Stage "Boss moves" scenarios "Stubborn (stays up at 1 HP)" and "Chance and trigger lines (Echo, Sidestep, Payback)".

**Sim (not tuned: Misa said no balancing now).** The sim plays the combat lines in its fights (the same engine; the luck dice come from the fight's seeded RNG) and does not play Tinker's luck or Second look. Gear share of fight-scored power, median at weeks 2, 8, 20 and 30, 20 servers of `leet:gear`, measured on this branch with the new lines off (their weights zeroed, which is the state before) and on: min-maxer 8.0, 23.3, 30.0, 30.3 to 7.5, 22.6, 28.6, 29.4; engaged 4.5, 13.4, 24.1, 26.2 to 4.4, 14.3, 24.9, 28.4; regular 3.0, 10.2, 17.7, 24.3 to 3.1, 9.3, 17.1, 22.5; drop-in 5.6, 4.5, 15.0, 21.4 to 5.3, 5.8, 14.7, 21.4. Every move is within about 2 points either way, the draws shifting (the pool is bigger, so every seeded drop of a Rare or an Epic is another item). ## 2026-10-17: items carry base stats; local and global lines; Festival gear is special, not stronger

ID: `2026-10-17-items-carry-base-stats-local-and` · Status: current, amended by `2026-10-17-staging-held-the-first-gear-v2` · Amends: `2026-10-16-gear-a-built-hat-scarf-and`

Misa's direction (2026-10-17), built on the gear v2 branch before it merges (so migration 27 and the conversion changed, no new migration). The design is `gear-and-creatures-v2.md` section 2.5; the numbers and their tuning are `docs/balance/log.md` B-018. Technical decisions by the lead and the implementer:

- **Base stats are fixed per base type.** A Hat carries Attack and HP (Attack-heavy), a Scarf HP and Attack (HP-heavy), and the finer bases a third stat the engine already has (crit chance or crit damage). They are never rolled and not scaled by item level: every Trail Cap is the same. Charms stay the mechanics slot and keep their implicit line. The kinds are one list in the content schema (`BASE_STAT_KINDS`), so a new kind is a data and fold change, not a redesign.
- **Growth comes from the local line tiers (still gated by item level) and from better bases that unlock at higher item levels.** Each slot and tag has three makes unlocked at item levels 1, 5 and 10 (`minItemLevel` in `gear.json`; 15 Hats and 15 Scarves). A drop picks evenly among the bases its item level unlocks; a craft needs a known blueprint whose base the crafter's item level (2 x Crafting level) unlocks (Crafting level 3 and 5), checked on the server (`base_locked`) and shown in the Workshop. The levels 5 and 10 follow the tier bands of the lines; the study preferred them to 8 and 15 (regular and drop-in players reach item level 5 and 10 in weeks, 8 and 15 left them on plain bases until week 25).
- **Local lines** ("+60% Attack (this item)") change one of the item's own stats: `(base + flat local) x (1 + percent local)`, percentages of one stat added. They roll only where the base has that stat, Hats favour the Attack ones and Scarves the HP ones, Charms never roll them. They replace the old percentage Attack and HP lines, Sturdy blow and the Hat and Scarf implicits. Global lines (crit, element, reaction, ward, Hunter, role, Guard's shadow, utility) are unchanged.
- **The plain percentage Attack and HP lines survive only as Creature Attack and Creature HP**, rare (weight 6) and on Charms only: creature talents of the same name use them, and a Charm that raises the whole creature is a real, if rare, choice. They never multiply an item's own stat (the fold adds the items' stats after the global shares). Thick coat stays as a talent-only line; Sturdy blow is gone.
- **Festival gear is special, not stronger.** No higher item level (the finale's `3 + Boss Rank`), no rarity floor (the finale's odds), no extra power. Festival is a **base**, not a rarity (`GearRarity` is Common, Rare, Epic; a Festival piece has one of them): it has one fixed unique line (Hearth warmth, Lantern luck: small utility effects, no Attack or HP), a narrow pool of five lines to roll from, base stats of a plain first-make piece, and its own look (a lantern-gold outline, a star, a Festival tag). Conversion turns an old Festival piece into a Festival base at the converted item level with a rarity drawn from the finale's odds; a database that already ran migration 27 has its Festival-rarity rows read as Epic (a one-line update at start, `convertPendingGear`).
- **Migration 27 changed in place** (its `rarity` CHECK no longer allows `festival`), as the lead allowed while PR #31 is unmerged. The glossary, the compendium, fixtures (captured from real server output), the Workshop and the workbench follow.
- **Sim.** The fold and every policy use the same pure functions (`itemStats`, `wornEffects`, `applyGear`, `itemScore`, `dropBase`); the crafting policy only picks blueprints the crafter's level can make. Base stats and local tiers were tuned toward the section 4 gear share targets (B-018); the raid was not tuned.

## 2026-10-16: Gear B: no free lottery (a craft's scrap follows the item level; a dismantle returns under half; a Reach needs no extra shards)

The lead's decision on B-013 (`docs/balance/log.md`), from Misa's rule that a dismantle returns "a fraction of its costs". Numbers are starting values; B-015 has the study.

## 2026-10-16: Gear B built: Reach, dismantle jobs, well-thumbed marks (migration 29)

After that rarity is drawn the **one-step-up chance** (1 point per Crafting level above 1, 1 point per well-thumbed mark, at most 10 marks) can raise it one rarity (Common to Rare, Rare to Epic). The craft always draws twice (the Reach, then the step up), so the result is exactly the shown odds. Every input is a whole percent, so the odds are exact in basis points (a test checks it for every Reach, level and mark count). The craft's XP follows its nominal hours (6 h: 72, 10 h: 120).
- **The server sends the odds; the client never computes them.** `POST /api/workshop/preview` (strict body, no key, changes and draws nothing) answers for a creature and a blueprint with all three ways to start: exact parts and Essence, time with that creature's Crafting level and Busy paws, XP, whether it is unlocked and the odds in basis points. It is a POST so the body is validated like every other request. The craft card shows the numbers up front (Misa's answer to the review page); "Details" holds the item level and the step-up explanation.

Jobs from before Gear B have none of them and read as a plain craft at the claim-time level.
- **Essence is spent through the ledger.** A Reach with Essence pays it with the keyed `spend` inside the keyed action (balance check, Essence debit, parts debit and job in one transaction; the client's key serves both the action row and the ledger, as the old upgrade did). Parts are checked first, so a short purchase takes nothing; short Essence answers 409 `insufficient_essence`; too low a level 409 `skill_too_low`; a retry with the same key returns the stored job.

To keep the screen lean the extra shards of a Reach on such a base are taken from the player's biggest piles (ties in element order), and the preview shows the exact bundle that will be taken. The plain craft of those bases stays scrap only (Gear A: the first craft must work on day 1). A choice of element can be added if Misa wants it.

Commons bundle (up to 5, 15 minutes whatever the count); a Rare takes 1 hour, an Epic or a Festival piece 2 hours, each alone (a mixed or repeated list is 400 `invalid_bundle`). The items leave the bag **when the job starts** (a worn one comes off with them; an item worn by a creature that is away or on a job is refused, see above), and a snapshot (base, rarity, item level) is kept in the job, so nothing can be lost or used twice and the inventory frees at once. Time uses the worker's Crafting level and Busy paws like any job; XP is 12 per nominal hour, at least 6 (a Common bundle pays 6), more with Apprentice.

The chance is shown in the preview. No "Tinker's eye".

The creatures step credits 4 experience per hour of a Workshop job from it (`gear-and-creatures-v2.md` 9.1) without reconstructing anything.

## 2026-10-16: Gear A built: Hat, Scarf and Charm, item levels, tiered lines, Equip best, conversion (migration 27)

ID: `2026-10-16-gear-a-built-hat-scarf-and` · Status: current, amended by `2026-10-17-items-carry-base-stats-local-and`, `2026-10-17-workshop-bag-polish-misa-s-feedback` · Amends: `2026-10-13-gear-and-crafting-v1-server-and`

Step 2 of the build order in `gear-and-creatures-v2.md` (section 14). Technical decisions made by the lead and implementer; the numbers are starting values in `RULES.gear` and the content files, and the sim reports where they land (`docs/balance/log.md` B-012).

- **The item.** `GearItem` is a base, a rarity, an item level (1 to 20, fixed when it drops or is crafted) and the lines it rolled (`{ id, tier }`, tier 0 to 4). A base is a slot (Hat, Scarf, Charm) and a tag (an element, a role for the role-locked Charms, `explorer` for the Crossroads Compass, or neutral); it brings one fixed base line whose value follows the item level's tier band. Rolled lines: Common 1, Rare 2, Epic 3, Festival 2 plus its glow. Everything is schema-validated data (`gear.json`, `gear-lines.json`); per-element lines (Attunement, Hunter, Ward, Reaction) are written once and expanded per element at load. Only the rolled lines are stored (`gear_items.lines_json`); text, numbers and "does nothing for this wearer" are worked out on the server for the gear view.
- **Tiers.** The best tier an item level allows is I from level 1, II from 5, III from 10, IV from 15, V at 20. A roll counts down from the best allowed tier with weights 15, 30, 30 and 25 percent (the best tier first; tiers further down cannot roll), so at item level 20 it is V 15%, IV 30%, III 30% and II 25%: the top tier is about 1 line in 7 (Misa's answer). The conversion rolls at tier II or better.
- **Line pools.** An element-tagged base weighs its own element's lines 3 times; a role-locked Charm weighs its role's lines 3 times and never rolls another role's; the Crossroads Compass weighs explorer lines 3 times and combat lines 0.3 times (weights are multiplied by 10 so 0.3 stays an integer).
- **Item level by source.** Finale `3 + Boss Rank`, Festival `5 + Boss Rank`, dungeon by depth with a landmark bonus, an expedition find twice the explorer rank (the Old Crossroads gives the Compass), a craft twice the crafter's Crafting level, the welcome Hat 1; at most 20. The finale gear takes the boss's element as its tag (1 Charm in 20 is role-locked instead), the dungeon the room boss's element, a trip the place's element.
- **The wear rule** is one pure function (`wearBlock`) used by the server, the sim and the client: a role-locked Charm only on its role, a slot opens at a creature level (Hat 1, Scarf 7, Charm 13) and the item's level may not exceed the creature's. The server answers `wrong_role`, `slot_locked` or `item_level_too_high` (409, with the level or role as the reason).
- **Equip best** is `planEquipBest` (pure, `packages/game`): for one creature or a team it considers the bag and what the planned creatures wear (never what other creatures wear), best pair first by `itemScore`, ties to the item already worn and then to the smaller id, and changes a slot only for a better item. `itemScore` is a deterministic stand-in in hundredths of power (Attack and HP counted exactly, every other line a share of power by its content `worth`, a quarter for a creature it is not meant for), not a fight; the player's own swaps beat it where position or this week's boss matter. The server takes at most 24 creatures; the Workshop's button plans for the three strongest, a creature card's for itself.
- **What lines do.** Stat and Attunement lines fold into the creature's stats and crit (`applyGear`, still capped by the luck room). The sheet lines fill `FightSlot.mods` with their conditions resolved to keyed tables (Hunter by the element it beats, Ward by the element that beats it, Reaction by reaction id, Guard's shadow by role). The trip and Workshop lines (Trail XP, Quick feet, Keen nose, Lucky find, Packer, Busy paws, Apprentice) are read by the server when a trip is sent or claimed and when a job starts or is claimed: Quick feet and Busy paws are capped at 50%. **Between-room rest** (a Scarf line) is a new dungeon input, `DungeonRunInput.rest`: a share of max HP recovered by a creature still standing when a room is won (`combat-rules.md` 2.1.2a). The "Tinker's eye" line is dropped (see the review answers above).
- **Removed, with clear answers.** Upgrades (`POST /api/gear/:id/upgrade` answers 410 `gear_upgrade_removed`), Improve and Enchant jobs (410 `job_kind_removed`), enchants, the speed and crit-as-roll stats, the old caps and the blueprint rarity. A job of those kinds that was running at the switch still finishes: it pays its Crafting XP, returns its parts and shows as an old job.
- **The conversion** runs once per player, inside the guild's Durable Object right after the migration (`convertPendingGear`), and is idempotent (`gear_conversion`; the old rows stay in `gear_legacy`). A worn item becomes the new item of its old slot kind and tint at the item level a fresh drop would have for that player today (`convertedItemLevel`: the higher of `3 + Boss Rank` and their best dungeon depth's drop level, at most 12), with its lines rolled at tier II or better, whatever its item level; it is taken off, with a reason, if its creature may not wear it. Unworn items are refunded as parts; upgrade Essence and scrap and enchant parts come back in full; blueprints map to the new bases. ## 2026-10-13: Gear and crafting v1 (server and content)

ID: `2026-10-13-gear-and-crafting-v1-server-and` · Status: current, amended by `2026-10-13-gear-numbers-set-by-simulation`, `2026-10-16-gear-a-built-hat-scarf-and`, `2026-10-21-the-bag-may-overflow-a-full`

The server and content half of `design/gear.md` ("v1 build spec") is in; the Workshop UI, sprites and the sim model come separately. Defaults held: one gear slot per creature, one shared busy state for expeditions and jobs, one skill (Crafting), no trading, no gear on sprites. All numbers are in `RULES.gear` and are starting values for the sim to tune.

- **Content.** `data/gear.json` has 19 bases: 5 neutral (3 Common, 2 Rare), 3 per element (a Common, a Rare and an Epic each) and 2 Festival bases (Tide lantern charm, Ember hearth band). `data/enchants.json` has 9 enchants: 4 by role (Payoff +6% Attack, Guard +8% HP, Setter +5% speed, Support +6% HP), 4 by element (Spark +3 crit points, Ember +10 crit damage points, Tide +4% speed, Grove +7% HP) and one for everyone (+3% Attack). An enchant that does not match the wearer shows as inactive. Parts: `scrap`, one shard per element, `glimmer`. Gear never reaches the engine: `applyGear` folds it into the stats and the crit bonus before the fight, so the engine, the combat tests and old replays are untouched.
- **Rolls.** Rarity gives secondaries (0, 1, 2, 2 for Festival) and a primary multiplier (x1.0, x1.25, x1.5, x1.5). Primary roll ranges in basis points: Attack 300 to 500, HP 400 to 700, speed 200 to 400, crit chance 100 to 200, crit damage 500 to 900; secondaries 100 to 250, 150 to 350, 100 to 200, 50 to 100 and 200 to 400. Each upgrade level adds a fixed step to the primary: Attack 80, HP 100, speed 50, crit chance 25, crit damage 150.
- **Caps per creature** (basis points): Attack 2000, HP 2500, speed 1000, crit chance 500, crit damage 2500. The gear's crit bonus also never takes a creature past the engine's room (30% chance and +150% damage in total), and a species that is already past it keeps what it has. With one slot, Attack and HP cannot reach their caps (an Epic +5 with the best roll and enchant stays under both); speed and the crit stats can. The caps are for a later second slot. A test checks every base, rarity, level, enchant, role and element, and that the best possible item (Epic +5, best rolls, matching enchant) adds between 10% and 25% to a mid creature's power. It is about 12%, and a typical Epic +3 is about 3%, so gear starts well under the 15 to 25% design ceiling: slow gear first, the sim decides how much to raise the numbers.
- **Upgrades.** Essence 20, 30, 45, 65, 90 and scrap 2, 3, 5, 8, 12 for +1 to +5, times 1.0 (Common), 1.5 (Rare) and 2.0 (Epic and Festival). A full Common costs 250 Essence and 30 scrap; a full Epic 500 and 60. Dismantling returns scrap 2, 5, 10, 10 by rarity, a shard of the item's tint (0, 1, 2, 2; none for neutral items), 1 glimmer for Epic and Festival, and half the scrap its upgrades cost.
- **Crafting costs.** By blueprint rarity: Common 6 scrap; Rare 12 scrap and 1 tint shard; Epic 24 scrap, 2 tint shards and 1 glimmer; Festival 24 scrap, 2 tint shards and 2 glimmer (neutral bases pay no shard). Improve re-rolls one secondary of a Rare or better item for 6 scrap (12 for Epic and Festival). Enchanting costs 1 glimmer and 3 shards of the enchant's own element. Durations: craft 4, 8, 12 and 12 hours by blueprint rarity, improve 2 hours, enchant 6 hours. A craft can come out one rarity higher (not above Epic; Festival stays Festival).
- **Crafting skill.** XP per finished job is its nominal hours times 10 (the skill shortens the time, not the XP). Levels 1 to 10 at 0, 80, 200, 380, 600, 900, 1300, 1800, 2500 and 3500 XP. Each level above 1 shortens jobs by 3% (27% at level 10) and adds a 1% chance of a craft one rarity higher (9% at level 10). A steady crafter (two Rare crafts and two improves a week) is at level 5 after a month; a casual one (one Rare craft a week) at level 3.
- **Drops.** Finale win, one roll per participant: Common 75%, Rare 22%, Epic 3% at Boss Rank 1; Rare gains 2.5 points and Epic 1.5 points for each rank above 1 (capped at 50% and 25%); the base is picked evenly among the normal bases. Cleared Phase 1 and 2: 3 and 4 scrap each. A won Festival finale also gives the Festival piece in the tint of the week's Festival creature, next to the normal roll. Expedition claim: scrap 1, 3 and 6 by duration (a recall pays the share that was caught and nothing else); a completed trip rolls one shard of the explorer's element (15%, 30%, 50%), and 12 hour trips a glimmer (5%) and a blueprint (10%; Common 60%, Rare 35%, Epic 5%, a base of that rarity). A blueprint the player knows becomes 5 scrap. Welcome kit (the first `GET /api/gear`, once): a random Common item, a random Common blueprint and 8 scrap, which pays for any Common craft, so crafting starts on day 1.
- **Inventory and workshop.** 60 items (crafts still in the workshop hold a place, so a claim can never find the bag full); 2 workshop slots. A drop that finds the bag full is turned into its dismantle yield (shown as `converted`), so loot is never lost.
- **Choices where the spec said "your choice".** Dismantling a worn item takes it off first (the in-page confirmation is the safeguard); an item in an open improve or enchant job cannot be dismantled or put in a second job. Enchanting an item that already has an enchant replaces it (the same enchant again is refused). Improve re-rolls the stat and the value of the chosen secondary (never a stat the item already has; the old one may come back). Equipping onto an occupied creature puts the old item back in the bag (the creature that held the moved item is left empty).
- **Busy state.** A creature is busy while it is away on an expedition or has an unclaimed job. Starting either refuses with `creature_away` / `creature_on_job`, a database index keeps one open job per creature and per item, and both kinds of busy creature still fight in raids. The collection view has `busy`, `gear` and `statsWithGear` for each creature (`stats` stays the stats without gear; `away` is expedition only).
- **Fights.** `loadCreatures` folds the worn item into each creature's stats, crit bonus and power at the moment a fight is built (phase resolve, live finale start, practice start, readiness forecast, party balancing and auto teams); `slotFor` puts the final stats and crit bonus into the fight slot. The stored input is therefore self-contained: tests show a fight with gear differs from one without, every stored fight replays exactly, an item changed, dismantled or levelled afterwards cannot touch a stored fight, and gear changed during the live finale does not reach the frozen fight. There is no separate "team freeze" moment: the stats of a phase are those at the moment it resolves, and the live finale is frozen at its start.
- **Idempotency.** Upgrade, dismantle, job start and job claim carry the client's key. `gear_actions (user, key)` stores the result and a fingerprint of the action; a retry returns the stored result, the same key on another action (or one a ledger spend used) is `key_conflict`. The Essence of an upgrade goes through the ledger's `spend` (check, debit, scrap and level in one transaction). Drops are idempotent per (player, key) in `gear_grants` (`raid:<week>:phase1|phase2|finale`, `festival:<week>`, `expedition:<id>`, `welcome`), draw nothing on a repeat, and use their own live RNG (`gearRng`), separate from the catch, fight and quirk RNGs. A claimed job stores its result and never rolls again; stored action results are pruned after 30 days.
- **Client contract.** `GET /api/gear` is `{ serverNow, balances, inventory, items, parts, blueprints, jobs, slots, skills, grants }`; the actions answer `{ result, gear, state }`. The loot of raids is not added to the Raid view (that would change every raid fixture); the loot reveal reads `grants` (keys above) for the week it shows. Expedition claims have `result.loot`. Fixtures were captured from real server output and the Worker's `gear-fixtures.test.ts` fails when the shape changes. New error codes: `insufficient_parts`, `creature_on_job`, `workshop_full`, `inventory_full`, `item_busy`, `not_ready`, `max_level`, `same_enchant`, `blueprint_unknown`, `nothing_to_improve`, `invalid_secondary`, `invalid_blueprint`, `invalid_enchant`, `item_gone` (plus the usual `key_conflict`, `insufficient_funds`, `creature_away`, `not_found`, `invalid_body`).
- **Analytics.** `gear_drop`, `gear_equip`, `gear_upgrade`, `gear_dismantle`, `job_start` and `job_claim`, one event per action that changed something, with content ids (bases, enchants), enums and integers only, rebuilt on write like the others. Raid drops are guild level (no actor); the rest carry the actor hash. The privacy scan covers all six.
- **Not done here.** Sprites and the Workshop UI; the daily dungeon's parts; the sim does not model gear yet (its slots are still without it, and its targets pass unchanged); nothing was balanced by simulation.
