## 2026-10-29: CI skips the build and tests for documentation-only PRs

ID: `2026-10-29-ci-skips-the-build-and-tests` · Status: current

Misa noticed that a PR adding only a retro file ran every CI job. He asked for a scope that saves CI time without leaving gaps.

1. **The workflow still runs on every PR; jobs are skipped inside it.** GitHub's `paths-ignore` would skip the whole workflow, and then the required `ci` check never reports and the PR stays blocked. Instead a small `changes` job (a checkout of two commits and `git diff --name-only` between the PR's merge commit and its base) decides, and the build and test jobs run only when it finds code.
2. **What counts as documentation is a short list; everything else is code.** Documentation is every Markdown file and everything under `docs/`, except `docs/compendium/`, which `packages/game/test/compendium.test.ts` reads. A new folder, a workflow, the lockfile or any file outside that list runs everything. That way, adding to the repo can never silently skip tests; the risk sits only in that list, and only one test reads from `docs/` today.
3. **Always run:** the formatting check (Prettier formats Markdown, and it caught a merge slip on 2026-10-28) and the security job (secret scan and workflow audits).
4. **`ci` accepts a skipped test job only when `changes` succeeded and found documentation only.** A skip for any other reason (`changes` failed, a job was cancelled) fails `ci`.
5. **A gap found on the way:** CI didn't run `packages/lab`'s tests (added in #92). The `test-rest` job runs them now (about 15 s).

## 2026-10-27: A generated wiki page of the game's configuration

ID: `2026-10-27-a-generated-wiki-page-of-the` · Status: current

**Decision (lead agent, for Misa).** `/wiki.html` is a reference page of what is in the game: every creature form (grouped by line, with stats, evolution relatives, its finale ability today, its current talents, and its combat v2 draft Knacks and talent pool), the current talents, and the combat v2 draft's Knacks, talents, keywords, Knack families, plus the elements. Each creature links to its talents and Knacks, which are entries further down the same page and link back to the creatures that have them (plain `#anchors`). The draft sections are labelled "Draft, not in the game yet". Design intent is shown, in a smaller style, because the page is for Misa too.

**Why build time, and why in production.** The page is generated from the content data (`@creatures/game`) and the lab's data (`@creatures/lab`) by a small Vite plugin (`apps/activity/src/wiki/`) on every build, so it can never be out of date and needs no hand-written text: a new creature, talent or Knack appears with no change to the wiki code (a test adds one to fake data and checks). It is one HTML file and one CSS file, with no JavaScript, so it fits the Content-Security-Policy (no inline style or script) and adds nothing to the app's bundle; the plugin loads the data modules with Vite's module runner outside the bundle, and the build test checks the production bundle still has no lab code. Unlike the combat lab and the workbench it ships to production and staging, because it is text that gives nothing away that a player could not read from the game's own screens, and Misa can open it from his phone on the live address. It is not linked from the game (the DEV panel does not link it either); it carries `noindex`, but it is not secret. Tests check every entry has an id, no link is dangling, every Knack of a form is linked, and text is escaped.

## 2026-10-26: A query plan audit and a day-in-the-life read budget

ID: `2026-10-26-a-query-plan-audit-and-a` · Status: current

The rows_read week showed that a per-path read budget is not enough: it only measures the statements somebody thought of, and it prices one call, not how often it runs. Misa asked for a system that catches inefficient queries before they ship. Three checks were added to the worker tests, all on the seeded month-old guild of the read budget test (now `test/read-world.ts`, shared):

1. **Query plan audit** (`query-plan-audit.test.ts`). Every distinct statement of the hot paths (start, login, the main GETs, alarms with and without the lounge, a lounge payment, a raid placement with a board listener) gets an `EXPLAIN QUERY PLAN`; a full `SCAN` of a table that grows with play fails, naming the statement, the plan and the `src/` call site. Walking an index (`SCAN ... USING INDEX`) is not a failure, because the read budget counts the rows. Small tables are allowlisted with a reason (`sessions`, which live an hour; `players`, `dm_prefs`, `games_medals`, `raid_readiness` and the one-row tables); `ACCEPTED` holds single statements, empty today.
2. **A day in the life** (`read-day.test.ts`). One game day of 10 players: 4 opens each, raid looks, board placements, 5 players lounging for 3 hours with the object evicted between minute ticks, every alarm of the day. It budgets the total (about 5% of the free tier) and prints the rows by source on failure. This is where frequency is priced, which was the root cause of the week.
3. **The lounge tick and a live board placement** are in the read budget test, with their own budgets, and in the growth check (together with `/api/state` and `/api/raid`, which used to be left out).

The audit found no scan worth an index: every full scan on a hot path was of a table bounded by design. The readiness band recompute (about 600 extra rows for a raid view every 5 minutes) is the biggest single line of the day and is the next candidate if the day budget needs to come down. Reasoning for the checks over a lint rule: a static check cannot see data sizes or bindings, and the plans are the database's own answer.

## 2026-10-26: What the rows_read week taught us (standing principles)

ID: `2026-10-26-what-the-rows-read-week-taught` · Status: current

Cloudflare stopped Durable Object requests twice in a week for passing the free tier's 5,000,000 rows read a day (#68, #85, #87, #88 fixed it: from several million a day to well under one million). The individual changes have their own entries above; these are the principles behind them, for every future feature.

- **The object sleeps after a few seconds; memory is not a cache.** With hibernatable sockets open, a guild object is evicted between the lounge's minute ticks and starts again on the next alarm or request. Anything kept in memory "for 5 minutes" (the readiness band, lounging time) is in practice recomputed or lost on almost every request. What must last between requests lives in a table (`raid_readiness`, `lounge_company`), and per-start work runs once per deployed build (`startup_passes`).
- **Measure, don't guess.** Every cut started from a probe that summed `cursor.rowsRead` per statement on a realistic month of data. Guesses were wrong twice: an index took the raid view only from 3,268 to 2,773 rows; the real cost was loading every teammate's whole collection. The probe is now the read budget test and the `db.rows_read` metric in the daily ops report.
- **Hot paths read a few rows** (CLAUDE.md, Conventions): every request, alarm tick and object start; an index for every lookup there; the read budget test with its growth check keeps it so.
- **Push the change, not the view.** A live socket is cheap (pings are answered by Cloudflare without waking the object) and a push can reuse the data the change already has: lounge XP (`lounge-xp`) and raid board cells cost a few rows or none, where a client reload of the whole state or view cost hundreds. A polling or reload loop on a timer is the last resort.
- **Record at the moment of change, never scan history.** The While you were away summary adds to one row per source at payout; the read is one indexed lookup.
- **Keep the stats, delete the details once nobody can use them** (Misa: "just record the stats and delete the details when players can no longer interact with them"). Old trips, Workshop jobs, Games shows, raid week details and sent posts go in the daily cleanup.
- **Don't guess for absent players** (Misa). Auto-picked teams for away players cost the most reads and only hindered the active players; a player now takes part by acting (placing), and what they did not do costs nothing.
- **Staging shares the account's quota**: its reads count against the same daily limit.

## 2026-10-25: The raid view stores its readiness bands and teammates' teams (migration 45)

ID: `2026-10-25-the-raid-view-stores-its-readiness` · Status: current · Amends: `2026-10-11-progression-phase-2-worker-and-client`

_2026-10-26: the stored teammate teams (`raid_team_cache`, `shownRaidTeam`) are gone: a team is just the placed creatures, loaded by id. The table stays (a released migration), unused. The stored readiness bands stay._

The raid view read about 2,800 rows on a month-old guild of 15 players. Nearly all of it was the party board: for every member, `raidTeam` loaded the player's whole collection (every creature, talent and worn item) to find their strongest unplaced creatures, on every view. The readiness band did the same through its forecast; it was cached for 5 minutes, but in memory, and the object sleeps a few seconds after each request, so nearly every view computed it again.

- **Stored readiness bands** (`raid_readiness`): the band per week and party with the week state, the time and a stale flag. The rules are the same as the memory cache had (a change marks it stale, recomputed at most every 30 s; without a change kept 5 minutes). Rows of other weeks are deleted when a band is stored.
- **Stored teammate teams** (`raid_team_cache`, `shownRaidTeam` in raid-teams.ts): the ids of each member's team as the view last worked them out. A view loads only those creatures by id, with their talents and worn items (stats always fresh). The ids are worked out again after 5 minutes, after any raid change (placements, teams, abilities, the roster: the same calls that mark the readiness stale), or when a stored creature is gone. Your own team is always worked out fresh. Only the choice of a teammate's strongest unplaced creatures can lag, by at most 5 minutes (a teammate who trained another creature). Fights never use it: `buildPhaseInput` works every team out from scratch.
- **The away list for a swap** reads only id, species, nickname and level of an away teammate's creatures (it loaded them as fighters).
- On the read budget's guild the raid view went from 2,773 rows to 780.

## 2026-10-25: Indexes for a player's recent trips and worn gear (migration 44)

ID: `2026-10-25-indexes-for-a-player-s-recent` · Status: current

The read budget test's growth check found two paths that read more every month: the state's recent claimed and cancelled trips (`expeditions_user_status` found the player's trips of that status, then sorted all of them for the newest few) and the raid view's worn gear per party member (`gear_items_user` walked every item of the player to find the worn ones). ## 2026-10-25: Lounge reads: one-row lounger, XP over the socket

ID: `2026-10-25-lounge-reads-one-row-lounger-xp` · Status: current · Amends: `2026-10-14-the-living-room-s-lounger-and`

The lounge was the next biggest source of Durable Object rows read. While players are in the lounge the guild alarm runs the lounge check every 60 s, and for each player in the room it read the player's whole creature list twice (the lounger lookup and its idle filter). Separately, the client reloaded the whole state (`GET /api/state`, 200 to 300 rows) every 2 minutes only to move the lounge XP bar.

- **Stored lounger, one row.** `Lounge.resolve` first checks the stored `players.lounger_id` with a query that reads only that creature (exists, is the player's, not away, no open Workshop job: the same busy rule as before, now as SQL). If it passes, the list is never read.
- **Deterministic re-pick, one query.** When the stored lounger is gone or busy, one `LIMIT 1` query walks `creatures_user` from the newest-caught creature and stops at the first free one, preferring creatures that are not Rested today (a second query, run only when every free creature is Rested). The open-job check uses the existing `workshop_jobs_creature_open` index, so no migration was needed. Misa chose this: "Pick the first creature in the player's creature list that is free sorted by ... desc", replacing the random pick; `pickLounger`, the lounger rng and their tests are removed. `Lounge.choose` keeps its 404 and 409 answers and reads one creature.
- **XP over the socket.** When a lounge payment commits, the payer's own lounge sockets get `lounge-xp` (creature id, XP paid today, level, experience, waiting). The client patches `loungeXp` and the creature's experience; a level-up or a ribbon wait does one normal reload. The 2-minute reload stays only as the fallback while the socket is not live. Values are absolute, so a missed push corrects itself with the next one.

## 2026-10-25: A read budget test and rows read in the ops report

ID: `2026-10-25-a-read-budget-test-and-rows` · Status: current

The account went past the free tier's 5,000,000 Durable Object `rows_read` a day twice in a week. Both causes (the alarm's cleanup, the start-up passes) were whole-table reads on paths that run every minute, and both were found by a hand-made probe after the limit was hit. Nothing in the tests or the report could have shown them earlier, because no test counted rows and the report did not know about reads. Two guards now:

- **A read budget test** (`apps/worker/test/read-budget.test.ts`) seeds a guild a month old and checks the rows read by an object start, an alarm, and the six hot reads, each against a budget of about 1.5x what it read when the budget was set. A growth check adds a second month and requires the alarm and `/api/me` to read no more than a few rows more: that is what a new whole-table scan looks like, and it fails before any budget would. The budgets sit next to the measured values, so a PR that raises one has to say why. `CLAUDE.md` has the rule.
- **Rows read in production, by source and game day.** `GuildCore` wraps its `SqlStorage` in a `ReadMeter` (`read-meter.ts`) that keeps the cursors the statements return; at the end of every request and alarm it adds the sum of their `rowsRead` to `db_reads` (migration 43), one UPSERT through the unwrapped storage, so the meter reads nothing and does not count itself. Sources are `start`, `alarm`, `socket`, and `request:<area>` for a fixed list of route areas (`request:other` for anything else), never an id. The daily rollup copies a finished day into `analytics_daily` as `db.rows_read` (dim `source`), the daily cleanup drops counters older than the analytics retention, and the ops report shows rows per day against the free limit, the top sources and an alert from 80% of a day. The report workflow is unchanged: the JSON already carries every metric.
- **Accepted:** attribution is approximate when requests overlap (the cursors of two requests that interleave at an `await` go to whichever flushes first); the day's total is exact. The start's rows are added at the next flush, since the table may not exist until the migrations have run. A login (`createSession`, over RPC) is `request:session`, the ops report's own RPC `request:other`. The counters add one row written per request and alarm, far inside the 100,000 writes a day.
- **What the first measurements showed** (15 players, 30 creatures each, a month of history): the start reads 45 rows, 43 of them `MAX(version)` over `schema_version` (one per migration, no index); an alarm 19; `/api/me` 25; `/api/room` 33; `/api/dungeon/today` 78; `/api/games` 253; `/api/state` 610; `/api/raid` 3,268. The last two are not constant: `/api/state` reads a player's claimed trips and `/api/raid` every party member's equipped gear, both through an index on the player that still walks all of the player's rows, so they grow with history (+120 and +480 rows for a second month). `/api/raid` also reads every member's creatures and talents (16 players, 2,158 rows for talents alone). They are budgeted, not fixed here.

## 2026-10-25: The start-up passes run once per deployed build

ID: `2026-10-25-the-start-up-passes-run-once` · Status: current · Amends: `2026-10-17-staging-held-the-first-gear-v2`, `2026-10-23-the-alarm-s-cleanup-runs-once`

Cloudflare stopped Durable Object requests for the day: the account went past the free tier's 5,000,000 `rows_read`, two days after the cleanup fix above. Production had one guild and about 8 players a day, so the reads came from work that repeats, not from big tables. A probe that counted the rows each statement read (12 players, three weeks of play) found it:

- **The cause.** `GuildCore.migrate` runs in the object's constructor, and after the numbered migrations it ran the start-up passes (gear row shapes, the gear and level conversions, missing talents, the `level_reset` lookup in `sqlite_master`). They read whole tables: 620 rows in the probe, more in production, growing with creatures, talents, gear and grants. The 2026-10-23 note left them as "a few hundred rows per start". But since the lounge's live sockets went on in production (2026-10-20) the object hibernates after a few idle seconds and starts again at the next alarm or request, and the lounge check runs the alarm every minute while anyone has the game open. So the passes ran about once a minute, all day.
- **Once per build.** The passes run on the first start of each deployed build and then a new `startup_passes` row remembers the build (`VERSION`, the git commit CI deploys). Later starts of the same build skip them: a start now reads about 43 rows. Each pass is idempotent and every deploy is a new build, so a branch switch on the shared staging database runs them again. Without a build (local dev, where `VERSION` is `dev`, and tests) they run on every start, as before. The table is made with `CREATE TABLE IF NOT EXISTS` where it is read, not as a numbered migration, so branches sharing staging never disagree about a number.
- **Level reset notice.** `pendingLevelReset` (every state load) asked `sqlite_master` whether its table exists (about 180 rows); it now reads the table and answers null on "no such table", as `booksByCreature` does.
- **The Games' day checks (migration 42).** Every request and alarm asked "a locked day not awarded yet?" and "entries on a day not locked yet?", and the Games tab "the latest shown day?" and "the latest awarded day?". Each read all of `games_days` (a row a day) or every entry of today's locked day. Three partial indexes on `games_days` (`games_days_unawarded`, `games_days_shown`, `games_days_awarded`) answer the first, third and fourth. `hasOpenEntries` now walks day by day (the first day with entries, is it locked, the next day), a few rows instead of a join over the entries. In the probe an alarm went from 130 rows to 30, the room check from 129 to 29 and the Games tab from 296 to 116.
- **Left as is:** the unresolved live finale lookup (about 14 rows, a row or two more each week) and the raid view's per-player talent reads (only when the raid page is open).
- **Staging counts too.** Staging runs on the same Cloudflare account, so its reads share the same daily limit.

## 2026-10-24: Faster lint, a staging check, check:changed and other fixes from the retro

ID: `2026-10-24-faster-lint-a-staging-check-check` · Status: current

From the retro of the raid finale visuals (`docs/retros/2026-10-24-raid-finale-visuals.md`); Misa asked for smarter fixes than more memory.

- **Lint per package, with a cache.** Type-aware lint builds a TypeScript program per package; one `eslint .` held all of them at once (about 4 to 5 GB) and ran out of Node's default heap (2.2 GB here). Measured alone, the client peaks at 1.5 GB at the default heap, the worker 1.7, the shared packages 1.1. Each package now has its own `lint` (ESLint's content cache in its `node_modules/.cache`), the root runs them two at a time plus the few root scripts: 90 s cold with no memory flags, 5 s warm, 2 s with one file changed. CI starts without a cache, so it always lints everything. Not the files' fault: no generated or data files are linted (JSON, dist and node_modules are not), and the cost is the type-aware rules, which stay. Tests are about a third of the client's code and most of the worker's; their type-aware rules (floating promises, unsafe any) catch real test bugs, so they stay too.
- **What is on staging, on demand.** `apps/worker/scripts/deployed.mjs` reads the branch and commit from the public `/api/config` of the two fixed game hosts (read-only, no URL from the caller; the repo still denies curl and wget), checks them against a ref and can wait until a commit is live. The new `staging` skill says when to use it; CLAUDE.md's deploy step uses it instead of asking Misa to read the footer. The deploy workflow's last step runs the same check, so a green run means the commit is live.
- **`pnpm check` and `pnpm check:changed`.** `check` is every check in order; `check:changed` runs lint, typecheck and tests for the packages changed since `origin/main` and those that depend on them (pnpm's `...[origin/main]` filter, the root excluded), so a worker change runs the worker's API contract tests while iterating.
- **The workbench registry test** asks for a page only for PascalCase exports of `src/ui`; helpers and constants there no longer fail it.
- **`scripts/shoot.mjs`** shoots a workbench page at 390 and 1100 px with a labelled sheet; `ux-patterns.md` asks for both widths every round.
- **`docs/design/review-brief.md`**: Misa's standing priorities for every UX review agent; a suggestion that trades against one goes to Misa as a choice.
- **The test page keeps style values**, so components driven by CSS custom properties are tested directly.

## 2026-10-23: The alarm's cleanup runs once a game day; old dungeon steps are deleted

ID: `2026-10-23-the-alarm-s-cleanup-runs-once` · Status: current, amended by `2026-10-25-the-start-up-passes-run-once` · Amends: `2026-10-13-daily-dungeon-v1-engine-content-server`

Cloudflare warned that the account had used 90% of the free tier's 5,000,000 Durable Object `rows_read` in a day. A local probe that counted the rows each query read (a month of play for 12 players) showed where they went.

- **The cause.** While any Activity instance is tracked, the lounge check runs the alarm every 60 s (`LOUNGE_TICK_MS`). Each alarm also ran the cleanup passes, and two of them read whole tables. The rollup's "last rolled day" (`MAX(day) WHERE metric = 'rolled'`) had no index, so it read all of `analytics_daily` (20,000 rows in the probe). The dungeon prune's `json_remove` and `act_json = '{}'` updates read every step older than 2 days, and old steps were emptied, never deleted (17,000 rows). That came to about 37,000 rows per alarm, about 2.2 million an hour while anyone plays, and it grew every day.

## 2026-10-13: Cleanup 1: one keyed-action helper and the key namespace rule

ID: `2026-10-13-cleanup-1-one-keyed-action-helper` · Status: current

Worker half of cleanup pass 1 (`cleanup-1-audit.md` section 10). No behaviour change; every key already stored stays valid. Decisions:

- **Client keys.** A client idempotency key (`IdempotencyKeySchema`, 8-64 characters of `A-Za-z0-9_-`, so never a `:`) is one namespace per player. It may sit in the ledger (a spend), in `gear_actions` (gear, workshop and expedition-send actions) or in `dungeon_runs`. A repeat of the same action returns the stored result; the same key for a different action (another kind, another fingerprint, or another table) is a `key_conflict`, and nothing runs or is charged.
- **Server keys.** Keys the server builds are `<source>:<scope...>` and always contain a `:`, so they can never collide with a client key. No migration.
- **Code.** `apps/worker/src/keyed-action.ts` holds `runKeyed` (gear and expedition-send actions), `keyTaken` (the cross-table check) and `settleSpend` (the answer of a ledger `spend`). `payOnce` in `gear-grants.ts` pays credits and grant of one server event under the rule above (the dungeon run and streak use it). One `GameError` and one `atomically` (`outcome.ts`) replace the four copies; `parseBody` is in `http.ts` and `IdempotencyKeySchema` in `schemas.ts`.
- **Coverage is deliberately not widened yet.** Today a gear or expedition key is checked against the ledger only, a dungeon key against the ledger and `gear_actions`, and a collection key (train, evolve) only by the ledger itself. Making every table check every other would be stricter, a behaviour change, and is harmless to skip while client keys are per-action UUIDs; it is a one-line change per caller (`keyTaken` takes the list of tables) if it is ever wanted.

## 2026-10-13: Live analysis and live-calibrated sim (`pnpm analyze`, `pnpm sim:live`)

ID: `2026-10-13-live-analysis-and-live-calibrated-sim` · Status: current

Phase 2 items 4 to 6 of `design/analytics.md`, in `packages/sim` (`live-report.ts`, `live-analyze.ts`, `live-render.ts`, `live-calibrate.ts`, `live-projection.ts`, the two CLIs under `scripts/`). No new dependency. Decisions:

- **The report is parsed again, not imported.** The sim package must not import from the Worker, so `live-report.ts` holds a strict valibot schema of `Report` (unknown keys refused; metric, dim keys and dim values match the same patterns the Worker enforces; bounded sizes). A report that does not match is refused whole. Every id printed in the output is in a code span, so report text cannot become Markdown.
- **Flags and the small-sample rule.** A rate raises a **flag** from `MIN_N = 20` samples (`MIN_PLAYER_DAYS = 30` active player-days for resources), a **watch** from `WATCH_FLOOR_N = 5`, and nothing below that. Thresholds are named constants in `live-analyze.ts`: nobody picks (a known option at 0, flag from 30 picks or offers, watch from 10), everybody picks (above 60% in a group of at least 4 options), depth wall (clear rate drops by more than 40 points between consecutive depths, both with at least 10 runs; a flag needs 20), finale band 40 to 60% per rank (Festival weeks excluded, they are eased), a currency piling up (in at least 3 times out, and a net per active player per day at or above `PILE_NET_PER_PLAYER_DAY`: bait 25, essence 2, scrap 5, shards 2, glimmer 1, supplies 3) or running dry (out above in), and an expected sink with no use while its currency has sources (`EXPECTED_SINKS`). The pile amounts were chosen from the sim's per-player income (a daily player earns about 50 Bait and 3 Essence a day) and are meant to be tuned from real reports.
- **Which sim targets are checked against live values.** Only those with a clean live equivalent (`LIVE_TARGETS`): Phase 1 and Phase 2 clear rate and finale win rate (as "typical group" targets, compared only when the average group is 5 to 10 players, else "not comparable"), the Festival finale win rate, dungeon depth 1 clear rate, the dungeon's share of Essence, and the element share of raid team slots. Everything else needs per-player data, levels or timings that rollups do not carry.
- **Calibration heuristic.** Sessions per active player-day `s` gives the heavy share `h = s - 1` (a casual has 1 session on an active day, everyone else 2, the sim's own check-in convention), and the casual share of players follows from casuals being active 2 days in 7. The server size is the average daily active players per server divided by the active fraction (3 to 30 players). A bounded coordinate search then fits `tripPercent` (share of check-ins that send trips) to trips sent per active player-day and `dungeonPercent` to dungeon runs per active player-day, and may move the casual share by at most 20 points. The fit error is the mean relative gap. Daily against top is fixed at 2 to 1 (they differ by one leet day; aggregates cannot tell them apart). New players are not modelled. Supplies per trip are compared but not fitted.
- **Two new sim knobs.** `EconomyOptions.behaviour` (leet days per archetype, `tripPercent`, `dungeonPercent`). Left at their defaults a run draws the same numbers as before (a test checks it); the extra random stream is only read when a percent is below 100.
- **Projection.** Seeded and reproducible (`--seed`, default `leet`; `--quick` for a small server and few sims). The sim starts from an empty server, because reports carry no holdings; `--age-weeks N` shifts the table to start at week N+1 of the server's life. It reports the first week a stockpile passes 4 weeks of its own income (and 50), the week dungeon depth growth falls under the band, and the week-bound sim targets (casual level at week 4, daily species at week 6, power ratio at week 8) as this server meets them. Outputs go next to the live report: `live-YYYY-MM-DD.md` and `.json` from `pnpm analyze`, `live-YYYY-MM-DD.calibration.json` and `.projection.md` from `pnpm sim:live`; an earlier calibration in the same folder is shown as parameter deltas.
- **Skill.** `.claude/skills/balance-review/SKILL.md` describes the loop for agents: report from the workflow log, analyse, project, log entry, scalar proposal from the registry, Misa's OK, patch notes.

Server side of `docs/design/dev-tools.md`, staging only.

- **Gate.** A Worker var `DEV_TOOLS` ("on" or "off"), set like `RAID_PRACTICE`: `"off"` at the top level and in production, `"on"` only in the staging env of `wrangler.jsonc`. A test parses the file and pins this. Every route under `/api/dev/*` answers a plain 404 (`{ "error": "not_found" }`; see the correction of 2026-10-13 below) unless the var is "on". The check is the first thing the Worker does for `/api/*` (before the session check) and the first thing the Durable Object does, so it holds even if one layer is bypassed. `GuildCore` only builds the dev tools when the var is on (`GuildCoreOptions.devTools`), so with it off none of that code runs. When it is on, `/api/config` and `/api/me` carry `devTools: true` (the key is absent otherwise) so the client panel can be loaded lazily. Dev routes still need a verified session, take the identity from it (no body carries a user id) and share the per-player rate limit.
- **One template route.** `GET /api/dev/state`, `GET /api/dev/events` and `POST /api/dev/<tool>` live under one template (`/api/dev/:tool`), with the tool ids in `dev-schemas.ts` (`DEV_ACTION_TOOLS`). Each body is a strict schema; each tool runs in one transaction and is logged as an analytics event `dev_action` with the tool id as its only prop (reports must exclude the kind). A refused tool rolls back and logs nothing.
- **The dev clock.** A per-guild offset in ms (an integer from 0, at most ten years) stored in the guild's Durable Object. `GuildCore` builds one `now` and gives it to every game module (collection and expeditions, gear, the dungeon, the raid, Discord posts, the leet sync, the alarm): it is exactly the real clock when the var is off, even if an offset is stored, and the real clock plus the offset when on. Sessions (creation, expiry), the rate limit and the "may manage the server" cache keep real time, and so does analytics (its events and retention are about the real world). The clock only moves forward (`advanceMs` up to 30 days a call, "to the next 13:37", "to the next raid event", or a phase of the raid week) and "reset" puts it back to zero; moving it back is not offered because stored game state (finished trips, resolved phases) cannot move back with it. Alarms are real time: the target is computed on the shifted clock and the offset is subtracted before `setAlarm`, and `ensureAlarm` compares in real time; moving the clock re-arms the alarm at once.
- **Where forced state lives.** A small key/value table `dev_state`, created with `CREATE TABLE IF NOT EXISTS` when a Durable Object starts with the var on. It holds the offset and the force flags (the next push-on offer and result, forced night and Festival per player, the dungeon day's picked modifiers). It is not a numbered migration, on purpose: production databases never get the table, and no migration number is spent on a staging tool. The game modules read flags only through an optional `dev` dependency that is `undefined` when the var is off, so a flag that is stored anyway is never read. A test pins that for the clock, night and the modifiers.
- **Tools write the tables directly** (they set a state for testing; they do not play the game), but still refuse what a rule forbids outright: a level above the species' cap, a rarity a gear base cannot have, a full bag, a roster after Phase 1 locked it.
- **Simulated players** for the raid have ids like `dev-guest-3` (never a Discord snowflake), three creatures of three lines near the caller's level (drawn from the live crypto RNG) and the automatic team; the row auto-places them when a phase resolves. "Run a full simulated week" resolves Phase 1, Phase 2 and the finale (as an instant finale, abilities at their default round) with the real resolver, so payouts, the ladder and the after-action are the real ones.
- **Live finale now** is the existing practice fight with a shorter countdown and without the finale block and the cooldown (`Raid.startPractice` options, passed only by the dev tool, which does not need `RAID_PRACTICE`).
- **Analytics rollup** is a hook (`DevToolsDeps.rollupNow`, marked TODO) that the rollup work wires; until then the tool answers 501.

## 2026-10-13: Analytics phase 2, server side: rollups, guild directory, ops report

ID: `2026-10-13-analytics-phase-2-server-side-rollups` · Status: current, amended by `2026-10-13-analytics-security-review-fixes`

Built per `design/analytics.md` (steps 2 to 5, phase 2 items 1 to 3 and 6). Decisions:

- **Rollup day is the game day.** The guild alarm rolls up each finished game day (13:37 to 13:37 guild-local, `gameDay`, `gameDayEnd` and `RULES.daily.reset`, with the timezone passed in) into `analytics_daily (day, metric, dims_json, value)` (migration 20). A row's `day` is the date the game day started on. The rollup runs at reset plus 3 minutes (13:40), the same slot as the leet sync, so one alarm serves both. Recomputing a day deletes and rewrites its rows in one transaction. A `rolled` row marks a finished day (also an empty one); the last rolled day is the newest `rolled` row, and a run catches up from the day after it, at most 14 days back. Raw events still prune at 90 days; rollup rows are kept 400 days. Events of kind `dev_action` never count.
- **Where each flow comes from.** Bait and Essence flows come from the `ledger` table (every row has a source label). Parts and supplies come from events. To get per-kind parts, `gear_drop`, `gear_dismantle` and `job_start` now carry a `parts` prop (kind to amount, only kinds that are present), and a supply `job_claim` carries `yield`. Events from before that fall back to the old totals (`shard-any` for shards). Finale abilities (hand-fired, held, Auto) are read from the `raid_live` table, not from events. Rollups hold counts only; distinct players (DAU, new players, watchers, users per feature) are counted from the hashed actors and only the count is stored. Every dim value is re-checked on write (id-like string or integer, never a hash-like run).
- **One guild directory object.** `GuildDirectory` (SQLite Durable Object, one instance named `guild-directory`) stores `guild_id, first_seen, last_seen` (UTC days). It is the only cross-guild index. `GuildWorld.createSession` tells it at most once per UTC day per guild object (in memory), without awaiting: a failure is logged by type only and never delays or fails a login. It has no HTTP surface. Both Durable Object classes are bound in every environment; the `v2` migration tag (`new_sqlite_classes: GuildDirectory`) is at the top level only because wrangler environments inherit `migrations`.
- **The ops endpoint.** `GET /api/ops/report` is authorised only by `Authorization: Bearer <OPS_TOKEN>`. `OPS_TOKEN` is an optional Worker secret: unset or empty, a wrong token (including a session token), or any method but GET all answer the same plain 404 (corrected 2026-10-13 below: not hidden, since unknown `/api/*` routes answer 401). Tokens are compared as SHA-256 digests with `crypto.subtle.timingSafeEqual`. A 429 rate limit (burst 5, then one request per 10 seconds) is keyed by a hash of the connecting IP and comes after the "unset" check and before the token check, so guesses cost tokens. Query parameters are strict (`from`, `to`, `format`, `weekly`, `compareFrom`, `compareTo`; unknown or repeated parameters are refused; at most 92 days). `weekly=1` compares with the previous period of equal length; `compareFrom` and `compareTo` give an explicit one.
- **Aliases, not guild ids.** A guild shows up as `g-` plus the first 6 hex characters of an HMAC-SHA256 of its id, under a key HKDF-derived from `DISCORD_CLIENT_SECRET` with its own info label (`analytics-guild-alias-v1`). The prefix grows (8, 10, ... characters) only when two guilds in the directory would collide. It is stable while the secret is the same, and not reversible without it. The report holds no user ids, actor hashes, guild ids, names or free text; every rollup row is validated again in the Worker before it can appear. Privacy tests seed distinctive ids, nicknames and hashes and check both formats.
- **Report workflow.** `.github/workflows/report.yml` runs daily at 06:17 UTC (and on demand) in the `reports` environment. It has no checkout and uses no third-party action: only `node` on the runner and a script inside the workflow, so it needs no permissions and no pinned SHAs. Mondays add `weekly=1`. A 404 (token not set yet) is a warning, not a failure. The deploy job passes `OPS_TOKEN` to the Worker like the other secrets, but optionally: an empty value is not uploaded and does not fail the missing-secrets check. Keeping the files as an artifact needs `actions/upload-artifact` pinned to a SHA, which no workflow here uses yet, so for now the Markdown and (collapsed) JSON go into the job summary.

## 2026-10-13: Analytics event log (step 1 of `design/analytics.md`)

ID: `2026-10-13-analytics-event-log-step-1-of` · Status: current

The per-guild event log is in, invisible to players: no route reads it yet, and rollups, the guild directory, the ops endpoint, the report workflow and `OPS_TOKEN` come later.

- **Schema (migration 16).** `analytics_events (id INTEGER PRIMARY KEY, at, kind, actor_hash, props_json)` with an index on `at`; `analytics_seen (actor_hash, last_at)` for session detection; `analytics_once (key, at)` for once-only marks (one live join per player per finale). Times are UTC epoch ms.
- **What is logged** (`analytics.ts` has the typed union and the writer): `session_start`; `starter_chosen`; `expedition_send`, `expedition_claim` (each catch with species, rarity, shiny and new/fused/converted, plus how long it waited) and `expedition_recall` (how much of the trip had passed); `train`; `evolve`; `fuse` (one per catch that fused or paid Bait); `roster_optout`; `team_set`; `placement`; `ability_pick`; `autofire_toggle`; `live_join`; `live_action` (fire, hold, unhold: the round, and the default round); `phase_result` (guild-level: boss, rank, festival, party size, win, rounds, and the top contributor's damage share in basis points, no per-user id); `rank_change`; `festival_grant` (species and result, no player); `post_result` (sent, retry or failed, with the error kind only).
- **Privacy by construction.** Props hold only content ids (species, boss, ability), enums, integers and booleans, and every value is re-checked against content or a fixed list when written, so an unknown value becomes `"unknown"` and free text cannot get in. `props_json` is capped at 1024 characters. A privacy test scans every event of a broad scenario for user ids, display names, nicknames, the guild and channel ids, the client secret and bot token.
- **Actor hash.** First 128 bits (32 hex characters) of HMAC-SHA256 of the Discord user id, with a key HKDF-derived from `DISCORD_CLIENT_SECRET` (the same secret source as session tokens, own salt `leet-creatures/analytics` and info `analytics-actor-v1`). Stable for one user, not reversible from reports. Rotating that secret changes every hash (it already signs out everyone), so retention numbers restart at a rotation. Web Crypto is async and Durable Object transactions are synchronous, so the hash is computed once per request, before the transaction, and cached per user in memory; the writer only reads the cache (a miss gives a NULL actor, never a raw id).
- **Written where the action commits.** Each event is a single INSERT inside the transaction of the action, so it exists if and only if the action committed. Replays of a stored result (same idempotency key) and repeats that change nothing (the same team, ability pick, opt-out value, slot, or Auto fire setting; hold on an ability that is already held) log nothing. Writing never throws, so logging cannot undo a game action.
- **Sessions.** A request from a player whose last activity is more than 30 minutes old logs `session_start`; the "last seen" mark is written at most once a minute per player, so a normal request costs no write.
- **Retention.** The guild alarm deletes events and the support rows older than 90 days, in batches of 500 (at most 20 batches per alarm); if a backlog is left, the alarm comes back a minute later.

## 2026-10-10: Per-guild timezone

ID: `2026-10-10-per-guild-timezone` · Status: current · Amends: `2026-10-10-scheduling-in-helsinki-time`

**Decision.** Each guild's timezone is stored in that guild's data (`guild_meta.timezone`, an IANA name, added by migration 5) and `Europe/Helsinki` is only the default (`DEFAULT_GUILD_TIMEZONE`). ## 2026-10-10: One Durable Object per Discord server

ID: `2026-10-10-one-durable-object-per-discord-server` · Status: current

**Decision.** Each Discord server (guild) gets one `GuildWorld` Durable Object that owns all game state for that server in its embedded SQLite database: players, creatures, ledger, raids, schedules. The Worker authenticates the request and forwards it to the guild's object.

**Reasoning.**

- A Durable Object processes requests one at a time with synchronous SQLite transactions, which makes double-spending and duplicated rewards structurally impossible (no interleaving between balance check and debit). D1 has no interactive transactions, so race-safe spending there needs careful single-statement guards.
- 5–15 players per server is far below a single object's throughput (around 1,000 requests/second).
- Per-guild isolation supports multiple servers from day one **[Misa: build for multiple servers]**.
- Durable Object storage has point-in-time recovery (30 days).
- Activities launched outside a server (DMs) are not supported; the UI asks players to launch from a server channel.

## 2026-10-10: Hosting on Cloudflare, all-in

ID: `2026-10-10-hosting-on-cloudflare-all-in` · Status: current

**Decision.** One Cloudflare Worker at `creatures.misacorp.dev` serves both the Activity frontend (Workers Static Assets) and the API (`/api/*`, `run_worker_first`). State lives in SQLite-backed Durable Objects. No AWS backend.

**Reasoning.**

- A Discord Activity needs a backend for the OAuth code exchange (client secret), so static hosting alone isn't enough.
- Serving frontend and API from one origin keeps Discord's URL mapping to a single `/` entry, and relative `/api/...` calls work through Discord's proxy with no extra mappings.
- The live Sunday finale needs a long-lived, stateful, real-time process (WebSockets, server-driven rounds). Durable Objects with the WebSocket Hibernation API and alarms fit this directly. On AWS it would take API Gateway WebSockets plus Lambda plus Step Functions plus DynamoDB for connection tracking.
- One cloud means one deploy pipeline, one set of credentials, and one place to look when something breaks.
- Misa offered AWS + CDK (the leet bot already runs there). We considered it seriously. Its real advantages were EventBridge Scheduler's native time-zone support and free-tier pricing; DST handling is solved on Cloudflare by computing alarm times in `Europe/Helsinki` (see below), and Cloudflare's free tier is also enough to start.
- Infrastructure is code: `apps/worker/wrangler.jsonc` declares the Worker, routes, custom domains, Durable Objects, migrations and cron triggers. CI applies it. Nothing is configured by clicking, except the one-time API token and the Discord Developer Portal (which has no IaC option).

**Plan tier.** Start on the Workers **Free** plan. Workers Paid is $5/month **per Cloudflare account** (not per Worker); it raises limits for all Workers on the account and replaces hard limits with usage billing above generous allowances. Upgrade only if a measured limit blocks us (the most likely one is the 10 ms CPU per request on Free). Misa has approved the $5/month if needed **[Misa]**.
