## 2026-10-30: Concept art runs ahead of content, drawn with the art studio

ID: `2026-10-30-concept-art-runs-ahead-of-content` · Status: current

**Decision.** Sprites can be drawn before their creature, boss or item exists. Concept sprites live in `apps/activity/src/sprites/concepts/<set>.ts` under working codes (`void-guard`), with a kind, role and note but no name or stats, and nothing in the game imports them. They are drawn and checked with the art studio (`pnpm art <set>`, `apps/activity/scripts/art.mts`): a browser-free PNG renderer (a coordinate-grid zoom, 1x to 4x on the three panel colours, the silhouette, alternative palettes, a set sheet with the nearest shipped sprite) and one pure lint (`src/sprites/sprite-lint.ts`) that holds the art rules the tests used to copy. Every shipped creature and boss passes the lint (a test). New rule: a contrast warning for colours inside the outline that melt into the dark panels; it flags Cinder Wyrm and the Tar Leech, so it stays a warning, not an error. When the content lands the sprite moves into `data/` and the concept is deleted. Process: `docs/design/art-studio.md`. The first set is Void (four roles, pale moon-lilac with a starry window; compendium `world.md`, "Void"), not yet seen by Misa.

**Reasoning.** Misa wants art for upcoming creatures and places before their design, and easier art-making. Drawing the first Void concepts showed where the time goes: art outside the content could not be seen, the old contact sheet took about 9 s through Vite and Chromium, pixels were hard to name, and the rules lived only in tests (two copies of the same colour and silhouette helpers). The studio renders in about 0.2 s with the repo's own PNG writer, so drawing is a tight look-and-fix loop. The contrast rule came from the first Void drafts, whose dark hood and ears vanished on `--dusk`.

## 2026-10-28: Ribbons and medals on the creature card

ID: `2026-10-28-ribbons-and-medals-on-the-creature` · Status: current

Misa asked for a creature's ribbons and Valley Games medals on its card in the creature list: decoration only, no words, the card as small as before. He chose the look over several workbench rounds (four placements first, then this).

1. **Ribbons** hang as strips from the card's top edge, behind everything on the card (`CardRibbons` in `CreatureHonours.tsx`; the card gets `isolation: isolate` and the strips `z-index: -1`, so they sit above the panel and under all content). Gold is longest, then Silver, then Bronze; the highest is on the left, with one gap to the card's edge and between strips. A creature holds the lower ribbons too, so Gold shows all three. Colours are mixed 55% into the card's panel colour ("muted": in the background but noticeable), with a light outer edge and a dark line inside it in hard stops. Each strip starts 4 px above the card, as if hung over its edge, that part a little lighter, its corners cut. Misa plans to drop ribbons from the game later; the strips go with them.
2. **Medals** are small round pixel medals pinned over the card's top edge at the right (`CardMedals`), always three in a fixed order (gold, silver, bronze): a metal not won yet is a dark silhouette with no count, so the leftmost medal reads as the best at a glance (Misa, 2026-10-28; at first a metal with none was left out). A creature that has won no medal at all shows none. The count is on the face (at most 99 shown; Misa expects the card to be redesigned before any creature gets that far). Pins stay on the creature page only. The rows of the creature list are 16 px apart (was 12) so a medal never touches the card above.
3. **Both are hidden from screen readers** (`aria-hidden`): the creature page says the same in words (its Ribbons row and its Valley Games medals).
4. **Data.** `CreatureView.medals` (`{ gold, silver, bronze }`) comes from `games_creature_medals`, left-joined into the two creature reads of `collection.ts` (`CREATURE_SELECT`). The medal row is found by its primary key, so the state reads one row more only for each creature that has medals; no migration or index was needed. The read budget, query plan and day-in-the-life tests pass unchanged.

## 2026-10-26: A private note per creature

ID: `2026-10-26-a-private-note-per-creature` · Status: current

A player asked (#76) for a short note on a creature, next to Rename, to remember plans for it. Misa: a small text box, at most 256 characters.

1. **Storage.** Migration 47 adds `creatures.note` (TEXT, null for none). The note is a column of the creature row, so the owner's collection state, which already reads every row, carries it for no extra reads. `CreatureView` is only ever built for the owner's own collection, so nobody else sees a note; the room, raid and other views never read the column.
2. **Route.** `PUT /api/creatures/:id/note` `{ note: string | null }` (strict body, at most 2,048 UTF-16 units), owner only (404 for anyone else's creature, like a rename). `null` or empty removes it. Not keyed: saving the same text twice is harmless.
3. **Text rules** (`sanitizeCreatureNote`, `RULES.creatureNote`). Like a nickname, nothing is silently stripped: control, format (bidi, zero-width), unassigned, surrogate and line or paragraph separator characters are refused (`invalid_note`), but line breaks and tabs are allowed. NFKC, line breaks become `\n`, at most one empty line in a row, trailing spaces cut per line, ends trimmed, then at most 256 code points. Rendered as text only.
4. **Client.** A "Note" fold under Rename on the creature page, open when there is a note, with a text box (`maxlength` 256), a "12 / 256" count and Save (off until the text changed). The note stays through evolving and renaming; it goes only when the owner removes it.

## 2026-10-20: Fusion goes up in points, slowly at the top

ID: `2026-10-20-fusion-goes-up-in-points-slowly` · Status: current, amended by `2026-10-20-raids-harder-for-the-tick-economy`

Expeditions now bring many more duplicates, and with one level of fusion per duplicate the raid team was fully fused (fusion 5) within two to four weeks for committed players (the creatures study, 8 weeks: a min-maxer's team averaged fusion 4.0 by week 2 and 2.9 of 3 creatures at 5 by week 4; fusion was 13% of fight-scored power and 7% of the Attack + HP score). Misa asked for fusion to be more incremental, with the first levels easy and the last ones much harder, and to stay fairly hidden.

A creature now has **fusion points** (`creatures.fusion_points`, migration 37). Fusing a duplicate adds points by the duplicate's rarity (`RULES.fusion.pointsByRarity`: common 1, rare 2, epic 4; shiny adds nothing extra). Fusion level N is reached at `RULES.fusion.thresholds` cumulative points: 1, 4, 9, 18, 34 (1, 3, 5, 9 and 16 points per level; first set at 1, 3, 6, 11, 19 and steepened the same day, before release, so migration 37 was updated in place). The stat bonus per level is unchanged (`cumulativeBonusBp`, +20% at level 5): the measurement did not show a level worth too much, the cost is what changes. Points past the maximum are not stored; at level 5 Fuse is no longer offered and Recommended goes on to Release, as before. `fusion_count` stays and is always the level those points have reached, so stats, raids and the rest of the game read it as before. Migration 37 gives each creature the points of the level it has (0, 1, 4, 9, 18, 34), so no level drops. A row whose level was set without points reads as the level it has (never lower). Recommended keeps its order (teach, keep, fuse until max, release).

The client shows it quietly: the creature page says "Fusion 2 · 4/6" (level and points toward the next), and the Fuse row says what it gives ("+2 fusion", with "level up" when it reaches the next level). The sim answers duplicates with Recommended as before, adding the duplicate's points. Before and after numbers are in the PR description.

## 2026-10-19: Every XP multiplier multiplies, and one rule in `xp-boost.ts` pays and explains every gain

ID: `2026-10-19-every-xp-multiplier-multiplies-and-one` · Status: current · Amends: `2026-10-19-every-xp-gain-is-the-count`

Misa decided that every XP multiplier multiplies: a gain's total is the product of all its parts (the treat, each Boon and Omen, each gear line, each trip bonus), not the treat times one plus the shares added together. This replaces the additive note in the follow-up of "Every XP gain is the Count-up row" above (3x with +25% and -20% is 3 x 1.25 x 0.8 = 3x, no longer 3.15x). Reasoning: players read the breakdown as a list of multipliers, so the Total should be the lines multiplied out; the old rule made the lines not multiply out to the total when two shares met.

- **One rule, one parts array.** `xpBoostTotalBp(parts)` starts at the product of the treats' multipliers times 10000, then applies each share in order as `total = floor(total * max(0, 10000 + bp) / 10000)`; it is never negative. `applyXpBoost(base, parts)` is `floor(base * total / 10000)`, so a gain is always exactly its base times the Total the player sees, rounded down. The values stay far below 2^53 (a base of at most thousands, a total of at most a few hundred thousand), so the integer maths is safe.
- **The amount and the breakdown come from the same parts.** `tripExperience`, `dungeonExperience`, `raidExperience`, `workshopExperience`, `tripXp` (explorer XP) and the Workshop's Crafting XP all take the parts and call `applyXpBoost`; the worker passes the same array to `xpBoost` for the result's breakdown. `creatureXpParts` (treat, then the day's parts) and `dayCreatureXpParts` build the creature-experience parts in one place, for the worker and the simulator. The old summed path (`ExpWeather`, `withDay`, `plusBp`, summed explorer shares) is gone.
- **An effect whose content left stays in the amount.** `dayParts` names it "Weather" instead of dropping it, so a stored trip or job pays the same as its breakdown says. Stored data is unchanged (`xpBp`, `treatMultiplier`, `xpEffects` on trips and jobs); a trip or job stored with only a legacy total still gives one day part. The dungeon view keeps its old `treatTimes` and `dayEffects` fields for one more release.
- **Rounding.** Rounded down after every share, in the order the parts are listed (the treat first, then the day, then gear and trip bonuses as the worker lists them). The order can move the Total by one basis point at most, and the Total shown is the one that pays.
- **Balance.** No scalar changed. Where two or more shares meet (explorer XP from milestones, a twist, a push-on goal and gear; a Boon with an Omen on experience) the gain is now a little bigger when the shares are positive. The numbers moved by the rule are in the PR description; the simulator's tiny headline test moved with them (explained in `packages/sim/test/run.test.ts`).

## 2026-10-17: creature levels halved at the switch to training by activity, Bait refunded

ID: `2026-10-17-creature-levels-halved-at-the-switch` · Status: current

Misa's decision, for the testers who already hold levels bought with Bait. Done once per player, inside the guild's Durable Object, right after the migrations (`level-reset.ts`, `convertPendingLevels`); no new migration number (it follows Creatures B, migration 30, in the same release).

- **Rule.** Every creature's new level is `max(1, floor(old / 2))`, with no experience banked. Fusions, quirks, nicknames and species stay (an evolved creature stays evolved, even below level 15).
- **Refund.** The old training price from level L to L + 1 was `3 + 2 x L` Bait. The refund is that price, at full price (the catch-up discount ignored), for every L from the new level up to the old level minus one, summed over the player's creatures. Level 30 becomes 15 and gives back 705 Bait (L = 15 to 29: 3 x 15 + 2 x 330). Level 12 becomes 6 and gives back 120 (L = 6 to 11: 3 x 6 + 2 x 51). Level 1 gives back nothing. The numbers are written out in the module on purpose: `RULES.training` is gone and a one-time conversion must not move when rules are tuned. Levels that came from fusion or other means are refunded by the same formula; this is for testers, not exact fairness.
- **One transaction per player.** The level change, the ribbons, the talents, the gear check, the stamp and the Bait credit (ledger source `level_reset`, key `level-reset:<user>`) commit together; a failure leaves that player pending whole (the others convert, the next start retries) and a second run changes and credits nothing. A per-player try/catch like the gear conversion.
- **Who.** Migration 30 itself only adds columns (and still grants ribbons by the old level, which the reset then overrides). The list of players is made by the conversion the first time this code runs on a guild (the table `level_reset` does not exist yet; it is created and filled with every player who owns creatures in one transaction). A table made on the spot, rather than in migration 30, so it also works on a database that already ran migration 30 on staging, and so a player who arrives later is never halved.
- **Ribbons** follow the new level: Bronze above level 10, Silver above 20 (so after the reset nobody holds more than Bronze, and a creature at exactly 10 waits for it).
- **Gear.** Worn items the creature may no longer wear (item level or slot opening level above its new level) go back to the bag. Worn items already count against the bag cap of 60, so unequipping can never overflow it and no item becomes parts here. It runs after the gear conversion (migration 27): if that ran first its items are fixed up by the check; if it failed for a player and runs later it reads the halved level itself.
- **Talents.** A talent in a slot the new level does not open (slot 2 at level 20, slot 3 at 25, so every creature that had them) goes back to the creature's Talent Book (`slot` NULL), not lost. The reset runs before the talent rolls of migration 28, so a creature that has none yet only rolls the slots its new level opens.
- **Nothing else caches levels.** Raid teams, dungeon drafts and trips hold creature ids, and fights read the level live.
- **Notice.** `GET /api/state` carries `levelReset` (counts only: creatures, Bait, items unequipped, talents booked) until the player dismisses it with `POST /api/level-reset/dismiss` (the server remembers it); a player whose creatures were all level 1 gets no card. The card says: "Creatures now grow by doing things. Every creature's level was halved and you got back the Bait those levels cost: N Bait." plus a line for unequipped items or booked talents when there were some.
- **Analytics:** `level_reset` once per converted player (creatures, levels removed, Bait, unequipped, talents booked; no names). The Bait reaches the daily flows from the ledger (label `level_reset`).
- **Sim.** The journey sim starts every player fresh (no "existing player" scenario), so it has nothing to convert.

## 2026-10-17: new-species pity: after 60 dry rolls a species the player lacks; a creature at least every 10 rolls

ID: `2026-10-17-new-species-pity-after-60-dry` · Status: current

The lead's decision (B-014 follow-up): the catalogue pace had no friction that was not a lower chance. Server-side counters per player (`player_progress.pity_new`, `pity_creature`) count catch rolls since the player's last new species and since their last creature of any kind; both move with the trip claim in one transaction, so a retry or a concurrent claim cannot count twice or skip.

- **Rule (`RULES.catching.pity`, `rollTripCatch`).** After `newAfter` (60) rolls without a new species, the next roll brings a creature and it is a species the player lacks (searching the whole place including its deep species: by the drawn rarity first, then any); when the place has none, it is an ordinary catch. Whatever the species, the `creatureEvery`-th (10th) roll in a row without any creature brings one. A forced roll draws no randomness; species picks use the live rng as before (`crypto.getRandomValues`, drawn when needed). A run of misses of any length ends within 10 rolls with a creature.
- **Numbers from the sim** (2 seeds x 6 servers x 30 weeks; catalogue week for min-maxer / engaged / regular, share of regulars who finish, creatures a week for a min-maxer): no pity 7 / 12 / 28 (19%), 13.5; floor only (10) 7 / 12 / 28; N = 20: 3 / 6 / 17.5; N = 30: 4 / 7 / 20.5; N = 40: 4 / 8 / 22 (97%); N = 50: 5 / 9 / 23 (94%); **N = 60: 5 / 9 / 24 (81%), 14.9**; N = 70: 5.5 / 9 / 27 (92%). The floor of 10 adds about 1.4 creatures a week to a min-maxer (13.5 to 14.9, inside the 10 to 15 asked for) and about 1.6 to an engaged player (9.3 to 10.9).
- **Why N = 60 and not lower.** The regular's review target of 24 weeks is the only one pity can still reach: committed players roll 50 to 70 times a week, so any N below about 60 completes their catalogue in 3 to 5 weeks. Pity can only speed players up, so the review targets of 9 and 14 weeks for the min-maxer and the engaged player cannot be met with it; the `creatures-catalogue-*` targets now say 4 to 8 and 7 to 12 weeks (B-016). The floor of 10 is what limits the flood: with it the committed profiles stay at 10 to 15 creatures a week.
- **Not a flood.** Duplicates are still answered by choice (Teach, Fuse, Release, Keep); a forced creature that is a duplicate is an ordinary duplicate.
- **Analytics:** `catch_pity` (`new` or `creature`, species) when a roll was forced. The send and claim screens show nothing about it; the how-to-play says a long dry spell always ends with a creature.

The draw order is the pick, then the golden draw, so seeded tests can script both.
- **Existing players.** Migration 28 only creates the tables. Right after the migrations the guild object rolls every creature that has no talent yet, once, for each slot its level has opened (a level 20 Splashet line creature gets 2), never the same talent twice on a creature, with live randomness; a second call changes and draws nothing.
- **Slots.** Slot 1 at catch, slot 2 at creature level 20, slot 3 at 25 for rare and epic species (`RULES.talents.slotLevels`, `slotsByRarity`); a common stage-1 line reaches level 20 only after it evolves. A slot that opens is empty until a Teach or a book slotting fills it. An epic's signature talent is active from the start, in no slot. A talent in a slot the level has not opened does nothing.
- **The fold.** One pure function, `applyGear(stats, crit, wearer, items, talents)`, folds the worn items and the active talents into the stats, the crit bonus, the modifier sheet and the trip, Workshop and dungeon rules; the worker (raid, dungeon, the collection view, trips, the Workshop) and the sim call the same one. A talent that does nothing for the creature (a Guard's cover on a Setter) is flagged `idle` and says so on its card.
- **The Talent Book.** `creature_talents` holds every talent a creature has held, golden or not (a golden Bigger Splash and a plain one are two entries), with the slot it sits in or none. A slot holds one talent; the one a slotting or a Teach replaces goes back to being a book entry. Slotting from the book costs `RULES.talents.bookSlotBait` (10) Bait, is instant and idempotent: a ledger spend with the player's key, the slotting applied inside it, checked first (`not_found`, `slot_closed` with `needs_level_N` or `no_such_slot`, `not_in_book`, `already_slotted`).
- **A duplicate is a card.** A catch of a line the player owns is stored as a pending card (`pending_catches`) with the species, whether it is shiny, the talent it rolled and where it came from (a trip or a Festival win). Up to `RULES.talents.maxPending` (10) wait; the 11th settles the oldest with Recommended before anything else, and the claim says so (`autoSettled`). The answers are `POST /api/catches/:id/choose` with `teach` (creature and slot), `fuse` (creature), `release`, `keep` or `recommended`, and `POST /api/catches/recommended` for all of them. Every one carries the client's key and runs inside one `transactionSync` (`catch-choices.ts`, keyed in `gear_actions` like the Workshop): a retry returns the stored result, a second answer to a settled card is `not_found` (the same answer for a card that does not exist or is someone else's), and nothing is drawn when the player answers. A shiny duplicate still makes the creature it joins shiny, at the catch.
- **Recommended** is `recommend()` in `packages/game/src/rules/duplicates.ts`: Teach when the talent is new to the book (or golden over a plain one) and scores better than what an open slot holds (`talentScore`: Attack and HP counted exactly, other effects by their line's worth, a quarter when they are not meant for the creature, 0 when idle), else Keep when a branch is missing, else Fuse until five, else Release. Deterministic; ties go to the earlier creature and slot.
- **Release** pays parts by rarity and the creature's element and never Bait: Common 3 scrap, Rare 6 scrap and 1 shard, Epic 12 scrap, 2 shards and 1 glimmer (`RULES.talents.release`).
- **Keep is built and tested but not offered yet.** A line can have a second branch (`altEvolvesTo` in the species content, validated: same line, element and rarity, a stage-2 target of exactly one species, branches differ), and `creatures` now allows two creatures of a line (`UNIQUE (user_id, line, line_slot)`, `line_slot` 1 or 2), at most `maxPerLine` (2). Keep is offered only while the line has a branch the player does not own; no shipped line has a second branch, so the button is not drawn and the server answers `keep_not_offered`. The tests inject a branching line (`branchesOf`).
- **The Festival grant** uses the same rules: a new Festival creature (with its signature), or a duplicate card (`outcome: duplicate`, with the talent and the card's id in the grant view).
- **Fewer catches, a mix of finds (9.5).** Each catch roll of a trip brings a creature only with the chance of its length, `RULES.expeditions.lengths.<length>.catchBp` (Short 3%, Medium 6%, Long 18%, Day 18%, plus the lure's); a roll that brings none brings `findScrap` scrap (finished trips only), and the first draw of a roll is that chance, so scripted tests list it first. The first expedition still guarantees the Zipmouse. The dupe shield now starts at a streak of 3 (it was 4; fewer catches make a long streak rarer).
- **Lures are made from Bait.** A lure's supply content now says `catchBp` (added to every roll's chance: 5%, 9%, 15% for Plain, Sweet and Golden) and `newBp` (the chance, drawn only when a lure is carried, that the creature is of a species the player lacks: 25%, 45%, 70%); its blueprint costs a little scrap and `bait` (12, 30, 60), and only lures cost Bait. The Workshop takes the Bait when the job starts (a ledger spend, purpose `lure`, with the client's key); the job view and the analytics event carry `bait`. Lures are crafted only: trips and the daily dungeon no longer find them (`FOUND_SUPPLY_KINDS`), and the rank gifts that gave lures give a satchel or a lantern instead. The old rare-up and epic-up fields of a lure are gone.
- **Removed:** the duplicate-to-Bait conversion (`RULES.fusion.convertBait`, `RULES.expeditions.convertBp`, `expeditionConvertBait`). Claims stored before this still read: their catches show `fused` or `converted` as they were.
- **Migration 28** creates `creature_talents`, `pending_catches` and a rebuilt `creatures` (same ids and order, `line_slot`, the new unique key), and rebuilds `raid_festival_grants` (its outcome check now allows `duplicate`; it gains `talent_json`). Nothing else refers to a creature by anything but its id.
- **Analytics.** `talent_roll` (species, talent, golden, and `backfill` for the one-time roll of an existing creature), `duplicate_choice` (choice, whether the server chose, species, rarity, talent, golden) and `talent_slot`; the catch event carries the talent and golden flag and the claim result a `duplicate` outcome. Ids and numbers only; the ops report has a Duplicate column.
- **Sim.** The journey sim gives every creature its first talent, answers every duplicate with Recommended straight away, fills open slots from the book for Bait (strongest creatures first), and crafts a lure only with Bait in the purse and within a quarter of the week's Bait earned (`GEAR_POLICY.lureBaitShareBp`; training runs first). A new study (`creatures-study.ts`, `pnpm sim:creatures`, part of `pnpm sim`) reports catches, duplicates and their answers, new species, the week the base catalogue (every species a trip can find, 12) was complete, the Bait split and the talents' share of fight-scored power (`1 - without / with`, the same three creatures with their talents taken away). Targets `creatures-*` are reported against the shipped numbers.
- **UI.** Lean by default. A catch card shows its talent (a gold frame, and the word Golden, for a golden one); a duplicate shows four buttons with the recommended one marked; Teach and Fuse go straight through when there is one place for them and open a short list when there are several. The Collection tab lists waiting cards with "Apply Recommended to all"; a creature card shows its slots (a closed one says the level it opens at) and a Talent Book one tap away with a button per open slot (10 Bait). The send screen has one compact lure row; the Workshop shows a lure's Bait cost and whether the player has it. Keep is drawn only when the server offers it.

## 2026-10-11: Progression, phase 2 (worker and client)

ID: `2026-10-11-progression-phase-2-worker-and-client` · Status: current, amended by `2026-10-16-creatures-a-built-talents-the-duplicate`, `2026-10-25-the-raid-view-stores-its-readiness`

**Decision.** The Boss Rank ladder, seasons, Festival weeks, rank-scaled payouts, the Festival creature and the readiness band are live on the server and in the Raid tab (`docs/design/progression.md`, "Phase 2: what was built"). The lead's numbers and Misa's decisions are unchanged; these are the interpretations:

- **Storage (migration 12).** `raid_ladder` (one row: the server's `rank`, NULL until placed, and `best_rank`, NULL until a normal week is cleared). `raid_weeks` gets `rank`, `effective_rank`, `festival`, `season_index`, `festival_species` (the week's plan, fixed at creation) and `ladder_at`, `ladder_won`, `rank_after` (the ladder's done marker and result). `raid_festival_grants` (primary key week and user: the idempotency of the grant). `server_firsts` is recreated with a fourth kind, `festival`.
- **Old weeks.** A week that exists when the migration runs keeps every new column NULL (`season_index IS NULL` means "legacy"). Two cases **[lead's change after review]**:
  - **Pool not stored yet** (the deploy landed between the week's creation and its Phase 1, the likely case): at Phase 1 the week is ranked (`convertLegacyWeek`). The server's rank is used, or, if it has none, the server is placed at that moment with `placementRank` from the creatures its members bring, and the rank is stored on the guild. The week stores its `raidWeekPlan` (rank, effective rank, season, Festival) and the boss is scaled with the plan's effective rank, not rank 1 (rank 1 is far weaker than the old formula for a levelled server). From then on it is a normal ranked week: rank-scaled payouts, Festival rules if the calendar says so, and the ladder moves after its finale. Before Phase 1 such a week shows no rank and no readiness band (there is no boss to forecast).
  - **Pool already stored at Phase 1:** the pool is untouched, Essence and jackpot pay the base amounts, no Festival rules, and its finale does not move the ladder. The server is placed when the next week is created.

  The new view fields are null for a week that has no rank (`rank`, `effectiveRank`, `season`). The luck rules (crits) apply to every fight built after the deploy, so a legacy week's remaining phases have crits even though Phase 1 did not.

- **Placement** (`placementRank`, once, from the 3 team creatures of every roster member): at week creation if the roster is not empty. **Deviation from the brief:** on a brand-new server the week usually opens before anyone has a creature, so placement happens as soon as the week has a member (`syncRoster`, on the first view or action) instead of at Phase 1. Phase 1 is still the last chance. Reason: otherwise the boss card would show no rank, and no readiness band, for the whole first week. Everyone who is eligible joins in the same `syncRoster` call, so the roster is not split across two placements.
- **The week's plan** is `raidWeekPlan(weekIndex, rank)`, stored at creation. The Festival creature of a Festival week is stored with the week (`festival_species`), so a later content change cannot change which creature a week gives.
- **Server won** = at least half of the parties that played a finale won (integer maths: `won x 2 >= played`; a tie counts as a win) **[lead's decision; Misa can change it]**. The ladder moves once, in the transaction of the last party that settles (a party with no members is not waited for). A week where no finale was played changes nothing. The rank the ladder starts from is the week's stored rank. The best rank is the rank of a won **normal** week (a Festival win never counts).
- **Festival grants** (`festivalGrantOutcome`): to every member of every party that won, in the same transaction that settles the party, once per (week, user). New: a level 1 creature (origin `festival`, never shiny). Fused: +1 fusion. Converted: Bait by rarity, credited with the key `festival:<week>` and source `festival`. "First on server": a **new kind `festival`** (the species is the Festival creature; everyone who got it in the same Festival shares it), because "caught" would be wrong for it; this needed the `server_firsts` CHECK to be widened. Festival species cannot be caught: `rollCatches` only draws `catchable` stage 1 species and the content loader refuses a catchable Festival species; a worker test claims 80 expeditions to be sure.
- **Readiness band** (`raid-readiness.ts`): `forecastWeek` while the week is open or only Phase 1 has resolved (Monday to Friday evening), `forecastFinale` on the finale input the party would fight with now once Phase 2 has resolved, none once the finale has started. It uses a **separate injected Rng** (crypto in production; `readinessRng` in `GuildCoreOptions`), never `raidRng` and never a stored seed, and only the band leaves the server (`party.readiness`). It is cached in memory per party and week state; a new state (Friday's or Saturday's result) is computed at once, a change to teams, placements, ability picks or the roster is picked up lazily and never more often than every 30 seconds, and without a change it is refreshed every 5 minutes (which catches training). A forecast that throws gives `null` and never breaks the view.
- **API additions** on `GET /api/raid` (and every response that returns the view): `rank`, `effectiveRank`, `festival`, `festivalCreature` (species id), `season: { index, week }` (week 1 to 5), `bestRank`, `party.readiness`, and in `you.reveal` (and the live finale's `loot`) `rankChange: { before, after, festival, serverWon } | null` and `festivalGrant: { species, outcome, fusionCount?, bait?, firstOnServer } | null`. `rankChange` is null until the ladder has moved (a multi-party server's first parties see it only after the last party has finished). The displayed Essence and jackpot are computed with the same `payoutWeek` as the payouts.
- **Discord.** Monday: "Boss Rank N." and, in a Festival week, "Festival week: <creature> for every winner, bonus Essence." The finale post lists "Festival creature: <name> for <members of this party who got it>" and the rank line ("The server climbs to Rank N.", "Rank N stays.", "The Festival is over. The server eases to Rank N."), with "X of Y parties won." first on a multi-party server. The rank line is in the post of the party that settles last, because earlier parties do not know the result yet. Both lines come before the records list, so a long post cannot cut them off. All names are escaped as before.
- **Client.** Boss card: the rank tag, "Festival week" styling and the creature teaser, five season pips (week 1 to 5, the 5th is the Festival, each pip also readable as text), and the band as a word (Long shot / Even / Likely / Strong) with the hint "How ready your team looks". The loot reveal (Raid tab and live finale) shows the Festival creature and the rank sentence. Collection shows a "Festival" badge on Festival species and says they are not found on expeditions; no screen offers them as catchable. No inline styles, text only.

**Reasoning.** One stored plan per week and one done marker per ladder move make every step idempotent and replay-safe; legacy weeks are plain old data, so a deploy in the middle of a week breaks nothing; a separate readiness Rng keeps the forecast independent of any real fight.

## 2026-10-11: Progression, phase 1 (rules, content, simulator)

ID: `2026-10-11-progression-phase-1-rules-content-simulator` · Status: current, amended by `2026-10-16-the-raid-curve-replaces-1-4` · Amends: `2026-10-11-second-balance-tuning-pass`

**Decision.** Misa's progression decisions are built in the rules, content and simulator (`docs/design/progression.md`, "Phase 1: what was built"; measurements in `docs/balance/report-2026-10-11-progression.md`). The worker and client follow in phase 2. Choices and interpretations:

- **Crits are on** (`RULES.combat.luck`): 5% / +50% for every creature and for the boss, species bonus kept, caps unchanged. Fortune streaks and the damage spread stay in the code, default off (lead's call, delegated by Misa). Boss Attack stays at x1. Stored inputs carry the luck config they were fought with (the worker must copy `RULES.combat.luck` in; phase 2).
- **Boss Rank replaces scaling by average level.** `scaleBoss(boss, players, rank)`. HP = `baseHp x N^e x rankFactor`; the rank factor compounds **+40% per rank** (integer basis points, floored each step, rank 1 to 30); Attack follows the excess at half strength so higher ranks do not knock out the row, as the old level scaling did. **A smaller step does not fit the targets:** over 30 weeks a server's wins are its rank gains plus the season resets, so the long-run win rate (40 to 60%) and "median 2 to 4 weeks between rank-ups" need the server's whole growth to be worth only 4 to 6 ranks. At +20% the simulator gave 65% and a median of 1 week. This is a game-feel question for Misa (a big, visible step per rank).
- **Head count is weight-neutral.** Every signed-up player counts once whatever their level, so one veteran cannot inflate the boss and no per-player cap is needed (there is no per-player weight). The exponent is now **per boss** (optional `hpExponent` in content, else `RULES.raid.scaling.hpExponent` 1.1): one exponent could not keep every boss flat from 5 to 15 players (Backdraft, resisted reactions). Fitted on four seeds with the tuning tool.
- **Placement** (`placementRank(levels)`): once, at the server's first raid week, the rank whose HP factor is closest to the old rule (+12% per average level above 1).
- **Ladder** (`nextRank`): a finale win in a normal week +1; a loss keeps the rank; no demotion, no Resolve; never below 1. **A Festival win does not raise the rank** (interpretation: the Festival is a break from the ladder; its reward is the Essence bonus and the creature). A week with no finale changes nothing.
- **Seasons and Festivals** (`seasonOf`, `raidWeekPlan`): a season is 5 weeks, the 5th is a Festival, from the global week index (the number that rotates the bosses), so every server shares the calendar and nothing is stored. The Festival boss fights at rank - 3 and Essence pays +50%; after each Festival (won or lost) the rank eases by 1. Ease 3 makes the Festival a near-certain win (97%) and breaks every loss streak; ease 2 lets 5% to 10% of servers lose more than 4 in a row.
- **Festival creatures:** Lanternfin (tide, epic, support) and Hearthshell (ember, epic, guard), `festival: true`, never catchable; one per Festival by season index, alternating (`festivalCreatureFor`). A repeat is the usual duplicate (`festivalGrantOutcome`: fuse up to 5, then Bait by rarity). The content loader checks the flag (not catchable, not a starter, single-stage, has an ability).
- **Rewards scale with rank** (`essenceMultiplierBp`): x(1 + 6% per rank above 1), capped at x2; a Festival adds +50% on top; the multiplier follows the server's displayed rank, not the eased one; jackpot Essence scales the same way (`jackpotEssenceFor`). `essenceForStage` takes an optional week argument.
- **Readiness band** (`readinessBand`, `forecastFinale`, `forecastWeek`): margin = mean finale damage (5 fresh seeds, defaults, boss that cannot fall) over the HP left; thresholds 8000 / 8800 / 10300 basis points calibrated against the win rate of "skilled-ish" play (a third of the players timing well). Monday's forecast estimates the HP left from two simulated phases so the same thresholds apply all week.
- **Targets:** six new ones (long-run win rate per server size, Festival win rate, weeks between rank-ups, loss streaks), none loosened. The creature balance target now leaves out Festival species (compared, not enforced). **Phase 2 clears at 52% of the pool (was 54%)**: with crits on the Phase 2 and finale clear rates sit closer together, and the 70 to 85% target could not be met with boss HP alone.
- **Worker in this phase:** only what keeps it compiling: `scaleBoss(boss, players, 1)` (every server at rank 1), nothing stored.

**Reasoning.** The ladder's arithmetic (wins = rank gain + resets) makes the season reset the control for the steady win rate and the rank step the control for the honeymoon, so those two were tuned together; the Festival ease only has to make the relief week reliable. The remaining knobs were left where the targets pass on six seeds.

## 2026-10-10: M2 collection on the server (implementation choices)

ID: `2026-10-10-m2-collection-on-the-server-implementation` · Status: current, amended by `2026-10-16-creatures-a-built-talents-the-duplicate`

**Decision.**

- One creature per (player, line); the game rules live in the pure `@creatures/game` package and the Worker's `collection.ts` only applies them inside one `transactionSync` per action.
- Claiming an expedition rolls every catch inside that transaction from the live crypto RNG. Claiming again returns the stored result, so there is no second roll or payout. Claim needs no idempotency key: the expedition's `claimed` status is the key.
- Training retries are not re-priced: a repeated key replays the amount that was charged the first time (the level, and so the price, has moved on).
- A recall that earns zero catches does not use up the first-expedition Zipmouse guarantee (`expeditions_claimed` only counts claims that brought something back).
- Starters are chosen, not caught, so they do not create "first on server" records. A second starter request always answers 409, also for a repeated key; the client reloads its state.
- Every mutating route returns the fresh player state, so the Activity needs no second request. Errors are `{ error }` with 400 invalid, 404 not found or not yours, 409 conflict.

**Reasoning.** Everything stays server-authoritative and race-safe: the Durable Object runs one request at a time and each action has no `await` between its checks and its writes.
