# The reset: what is built

The plan is `docs/design/reset.md` (on the `reset-plan` branch until Misa merges it; accepted 2026-11-06). This file records the **server side as built**, and what the release PR still has to add. Decision: `pnpm decisions show 2026-11-15-the-reset-is-built-inert-a`.

## Built (inert)

Everything lives in `apps/worker/src/reset/`. Nothing in production reaches it: the only entry is a staging dev tool that reads.

### The wipe

- Refuses (`WipeRefused`: `no_receipt`, `wrong_archive_key`, `stale_receipt`, `bad_switch_day`) unless the receipt parses, names this archive key, and its settler and creature counts equal the live database. One transaction: a failure changes nothing.
- Drops every table except `guild_meta` (this server's Discord id, timezone and announce channel), `analytics_daily` and `db_reads` (hashed daily counts); copies those three through the rebuild; runs the migrations from zero; sets `leet_sync` to `(cursor NULL, since_date = switch day, source = the configured kind)`. A differing source kind would make the sync forget its start day and backfill `LEET_BACKFILL_DAYS` again, so the kind is part of it.
- **The caller then runs `GuildCore.migrate()`** (what a fresh object does at start): it adds what the start-up passes create (for example the level reset's table). The tests do this and compare with a fresh guild's row counts.
- The raw analytics events (they carry actor hashes), sessions and the dev state go with everything else.

### How it is kept inert

`test/reset/inert.test.ts` scans the worker's sources: nothing outside `src/reset/` imports from it except `dev-tools.ts` (the dry run); no file calls `wipeGuild` or names `SettlerArchive`/`SETTLER_HMAC_KEY` outside `src/reset/`; no dev action tool names the reset; the Worker entry imports nothing from it; `wrangler.jsonc` has no archive binding, migration or secret. The release PR changes this test on purpose.

## What the release PR must add

1. In `wrangler.jsonc`: the `SETTLER_ARCHIVE` binding, a Durable Object migration (`new_sqlite_classes: ["SettlerArchive"]`, next tag), and `SETTLER_HMAC_KEY` listed in the secrets (not required in the config's staging environment if staging uses a test key). Export `SettlerArchive` from `src/index.ts`. Call out `wrangler.jsonc` in the PR description.
2. The secret **`SETTLER_HMAC_KEY`**, which Misa sets in Cloudflare (and GitHub for CI). It must never be lost or rotated, or returning settlers can no longer be matched. Never in chat.
3. The trigger: on the first wake after the release, each server (a) builds the record (`buildSettlersRecord`), (b) `put`s it into the archive and keeps the receipt, (c) sends the DMs, (d) calls `wipeGuild` with that receipt, then `GuildCore.migrate()` and drops the object's in-memory caches (a restart of the object is the simplest). A server that cannot archive stays closed and does not wipe.
4. The "back soon" card shown while a server works, and the in-game "A new valley" card after (plan section 5).
5. The DM sending: one DM per settler through the existing DM sender (`dm-send.ts`) with `goodbyeMessage(...)`, to everyone once (also players with reminder DMs off), the Discord ids read from the live `players` table at that moment (the record keeps none), and the **24 hour cap**: wipe once the DMs are sent or 24 hours have passed. A closed DM is skipped. Rate limits of Discord's DM channel opening need pacing.
6. The record and the settler ids must be kept in one snapshot: the DMs and the archive come from the same `buildSettlersRecord` call. The settler list in the DM step has to map record to Discord id before the record is stored (the record cannot do it); the release code keeps that pairing in memory only for the run, or recomputes it by the keyed hash.
7. The switch day passed to the wipe is the guild-local day of the release (`record.switchDay`), and the leet source kind is the one `GuildWorld` configures (`http` in production).
8. Update `test/reset/inert.test.ts` for the new wiring, and add the trigger's own tests (a failed archive write never wipes; a retry after a crash does not double-send).

## Undecided

- **Where the DM pairing lives** (point 6): the plan keeps no ids in the record; the release step needs the pairing of settler to Discord id for one run. Proposal: build the record and the list of Discord ids together in memory, send, then discard; if the object restarts midway, rebuild from the live database (still not wiped) and the `idHash` ties the retry to the same people. A DM sent twice after a crash is possible; a `dm_sent` style mark would prevent it.
- **Whether `guild_meta` should be kept** (it is, so the object can ask the leet source who played). The alternative is a full wipe with the guild id re-learned from the next session; the leet sync then waits for the first session.
- **Record size**: a 15-player server is a few hundred KB of JSON; the archive refuses a record over 1.5 million characters (one SQLite row holds up to 2 MB). A larger server would need chunking.
- **Quirk**: stored as the quirk id, not its text, so later content reads the current wording.
- **A stage-2 line's name** in "First on the server" is the line's first form (stage 1). A line the content no longer has falls back to its id.
- Names and nicknames in the archive: before any is used in content, an agent reads the list once and Misa strikes any name (plan section 2).
